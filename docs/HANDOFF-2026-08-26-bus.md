## 다음 작업, 순서대로

**1. 실주행에서 시각이 맞는지 잰다 (가장 앞)**
시뮬레이터로 화면까지 확인했지만 **`999번 16:31 도착` 이 실제 도착과 맞는지는
실주행에서만 잰다.** 볼 것 넷 —
- 풍산역에 가까워질 때 칩이 뜨는지
- 그 시각이 실제 버스와 몇 분 어긋나는지
- 정류장에서 **서서 기다리는 동안 문구가 멈추지 않는지**(이번에 고친 자리다)
- 새로고침 `↻` 를 눌렀을 때 몇 초 걸리고 값이 바뀌는지

어긋나면 시각을 기억하고 배포 로그를 그 창으로 되짚는다. **서버는 UTC 로 찍는다.**
```
railway logs --service 14494695-8eee-4f32-a4ea-3e0a4bcfd785 --since <ISO> --until <ISO> --lines 5000 --json
```

**2. 정류장 목록에 경유 노선을 보여 준다**
이 회차에서 드러난 **원래 있던 구멍**이다. 경로를 만들 때 정류장 칩이 이름과
기둥번호만 보여 주고 **어떤 버스가 오는지는 안 보여 준다.**

```
풍산역   정류장 번호 20573      ← 실제로는 99 만 온다
풍산역   정류장 번호 20575      ← 81 · 99
풍산역   정류장 번호 58271      ← 87 · 96 · 999
풍산역   정류장 번호 20753      ← 81 · 87 · 96 · 999
```

네 개가 다 "풍산역" 이라 999를 적는 사람이 어느 기둥을 눌러야 하는지 알 방법이
없다. 잘못 골라도 저장할 때 아무 표시가 없고, 지도의 선은 노선 자료로 그려져
그럴듯하게 나온다. **이제는 도착시간 칩이 조용히 안 뜨는 것으로만 드러난다.**

로컬 DB 의 옛 경로 `회사-집 (10구간)` 이 실제로 그렇게 저장돼 있었다(999가 안 서는
20573). 사용자의 `퇴근길` 은 20753 로 제대로 저장돼 있다 — 5.5m.

막는 방법이 있다. **`getSttnThrghRouteList` 가 그 정류장을 경유하는 노선 전체를
준다**(지금 오는 버스와 무관). 이미 활용신청된 서비스라 **새 신청이 필요 없다.**

```
GET https://apis.data.go.kr/1613000/BusSttnInfoInqireService/getSttnThrghRouteList
    ?serviceKey=…&cityCode=31100&nodeid=GGB219000638&numOfRows=100&pageNo=1&_type=json
```
**파라미터가 `nodeid` 다** — 도착정보의 `nodeId` 와 대소문자가 다르다.

할 일: `/stops` 응답에 `routes` 를 더하고, `BusStop` 에 담고, 칩과 검색 목록에
한 줄 더 그린다. **한도가 1,000/일 이고 정류장 조회와 같은 계정을 쓴다** — 지도를
움직일 때마다 8회씩 나가면 태우므로 이미 있는 디바운스(250ms · 60m) 안쪽으로 묶고
프로세스 캐시를 둔다.

**3. 서울 버스 (막힘)**
`퇴근길` 의 163 구간은 `busNo` 가 비어 있어서 조회 자체가 안 나간다. 채워도 안 뜬다 —
서울 시내버스는 TAGO 에 없다. 서울시 TOPIS(`ws.bus.go.kr`)에 있는데 **지금 키로는
401** 이고 별도 신청이 필요하다. 응답이 XML 이고 `arrmsg1` 이 `3분54초후[2번째 전]`
같은 문자열이라 초로 바꾸는 함수가 하나 더 필요하다 — **그 형식은 키가 열린 뒤에
실제로 불러 보고 정한다.**

**4. 잠금화면 새로고침 버튼 (안 함)**
지금 `↻` 는 **앱 카드에만** 있다. 잠금화면에도 넣을 수 있다 — `CheckInButton` 이
이미 `LiveActivityIntent` 로 같은 일을 하고 있어서 새로 알아낼 것이 없다. 다만
인텐트 타입이 위젯에도 보여야 해서 `Shared` 에 두고, 네트워크는 앱 타깃에 있으므로
앱이 launch 때 핸들러를 등록하는 모양이 된다. 사용자가 앱 카드만 하기로 정했다.

## 오늘(오후) 한 일

### 버스 실시간 도착 — 노선도 칩

```
🚌 999번   16:31  도착 ·  2정류장 전   ↻
    그다음   16:50  도착 · 11정류장 전
```

**자료** — 국토교통부 TAGO `버스도착정보`. **서비스마다 따로 활용신청을 받는다** —
신청 전에는 같은 키로도 `403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 온다(키가 죽은
줄 알기 쉽다). 개발계정 **10,000/일**, 정류소·노선 서비스(1,000)의 열 배다.
신청: <https://www.data.go.kr/data/15098530/openapi.do>

**절대시각으로 적는다.** `10분 후` 로 적으면 갱신이 끊긴 동안 그 글자가 멈춘다.
정류장에 서서 기다리는 동안이 정확히 그 상황이다 — 위치 보고를 일으키는 것은
시간이 아니라 150m 이동(`distanceFilter`)이고, 풍산역에서 정류장까지가 78m 다.
`expectedArrival` 이 이미 같은 규율로 절대시각이다.

**호출 예산** — 승차 15분 전부터만, 30초 캐시. 정류장 해석은 성공하면 영구 캐시,
실패는 10분 뒤 재시도. 실제 경로를 5초마다 물어 세어 보니 **정류장 조회가 귀가
한 번에 2회**다(163 은 창 9분이 재시도 10분보다 먼저 닫혀 1회, 999 는 첫 조회에
찾고 성공은 영구 캐시라 1회).

### 이번 회차에 잡힌 것들

**`content_state()` 가 네트워크를 기다리는 함수가 돼 있었다.** 재보니 실측이 이랬다.

```
정류장 조회 (풍산역)            4,078 ms
정류장 조회 (서울 163)          2,592 ms   결과 0개
bus_arrival 999  (캐시 없음)    8,952 ms
bus_arrival 163  (서울)        12,883 ms
  163 두 번째                   4,409 ms   ← 실패가 캐시되지 않았다
```

앱의 위치 보고 타임아웃이 **8초**다(`App/Session/SessionReporting.swift:115`).
그리고 `handle_location` 이 `content_state` 를 **두 번** 불렀다. 163 구간의 창은
출발 직후 열리고(승차 540초 < 창 900초) 서울은 늘 실패하니, 귀가 내내 보고마다
4.4초씩 두 번이 얹혔다.

**이 기능이 자기가 기대는 길을 부수고 있었다** — 위치 보고 응답으로 상태를 받는
것이 오전에 만든 푸시 지연 우회로인데, 그 응답을 이 기능이 늦췄다.

고친 뒤: `arrival_ready` 는 **캐시에 있는 것만** 주고 없으면 배경 스레드로 미룬다.
**0.594ms / 0.138ms / 0.162ms** — 첫 호출은 값 없이 즉시 돌아오고 그다음부터 값이
나온다. `handle_location` 의 두 번 호출도 한 번으로 합쳤다.

**로컬 갱신이 값을 지우고 있었다.** 서버가 `999 · 15:59 도착 · 2정류장 전` 을
보냈는데 화면에 아무것도 없었다. `HomecomingActivityManager.update` 가
`ContentState` 를 **처음부터 다시 만들기** 때문이다 — 필드를 안 쓰는 것이 곧
지우는 것이고, `travelledMeters`·`delaySeconds` 가 예전에 같은 함정에 빠졌던
자리다(그 주석이 경고하고 있었다).

> **와이어에 필드를 더할 때 고칠 자리는 넷이다.**
> `CodingKeys` · `init(from:)` · `encode(to:)` · **`HomecomingActivityManager.update`**
> `CLAUDE.md` 가 셋만 적고 있어서 이 함정에 빠졌다. 그 문서를 고쳤다.

**정류장에 서서 기다리는 동안 값이 사라졌다.** `next_bus_leg` 이 "타고 있는 버스는
다음이 아니다" 로 현재 구간을 건너뛰는데, 진행도는 **저장된 시간표**에서 나온다.
버스가 늦으면 서 있는데도 승차 시각을 지나 "탔다" 로 판정됐다 — 하필 그 값이 가장
필요한 순간이다. 이제 **승차 지점 150m 안이면 아직 기다리는 중**으로 본다(풍산역
네 기둥이 130m 안에 흩어져 있고 이 저장소가 버스 픽스 정확도를 30m 로 잡는다).

**정류장 수는 늙지 않는다.** 시각은 절대시각이라 시계가 흐르면 스스로 맞아 가는데
`5정류장 전` 은 그대로 남아 거짓이 된다. 실측: 15:36 에 5, 15:37:55 에 3 — **약
57초에 한 정류장.** 그래서 `busArrivalMeasuredAt` 을 같이 보내고 60초 넘으면 그
숫자만 감춘다. 시각은 늘 그린다.

사용자가 네이버지도와 견줘 이걸 잡아냈다 — 우리 `15:42` 는 TAGO 의 `15:42:40` 과
6초 차이로 맞았고, `5정류장 전` 만 틀렸다(실제 3, 네이버 2).

**이미 지나간 시각은 주지 않는다.** 배경 갱신이 계속 실패하면 마지막 좋은 값이
그대로 남고, 절대시각이라 시계가 흐르면 과거가 된다 — 이미 떠난 버스를 가리킨다.
창이 15분이라 최대 15분까지 그럴 수 있었다. **엄격한 과거만 자른다** — 정확히
지금이면 "지금 도착" 이고 그건 참이다.

**시험 표본이 실제 응답과 달랐다.** `routeno` 가 문자열이 아니라 **숫자**로 온다
(`"routeno": 999`). 코드는 `str()` 로 감싸서 통과했지만 시험이 그 길을 한 번도
밟지 않았다. 사용자가 포스트맨으로 직접 날려 드러났다. 표본을 실제 응답 모양으로
고쳤다.

### 화면

**칩으로 키웠다.** 처음에는 구간 이름과 같은 10pt 흐린 글씨였는데, 정류장에서 폰을
꺼내 이걸 보려는 사람에게는 안 보였다. 시각이 15pt 굵게, 노선번호는 배지, 색은 카드
강조색, 둥근 배경.

**`Grid` 로 칸을 맞춘다.** 두 줄이 나란히 있을 때 시각끼리·정류장 수끼리 세로로
서지 않으면 "몇 분 더 기다리나" 를 견주기가 어렵다. 아이콘을 **별도 칸으로 빼서**
`그다음` 이 `999번` 바로 밑에 선다. 시각 칸은 오른쪽 정렬.

**크기로 위계를 주면 정렬이 깨진다.** 둘째 줄을 작게 했더니 칸 폭이 달라져
`도착` 과 정류장 수가 몇 px 밀렸다. 크기는 같게 두고 **흐림으로만** 위계를 준다.

**새로고침 `↻` 는 귀가자에게만.** 가족은 남의 세션을 새로 조회할 수 없고, 눌러도
아무 일 없는 버튼은 없는 것보다 나쁘다. `RouteStripView` 가 클로저를 받고, 안
넘기면 안 그린다.

**`POST /session/{id}/bus-arrival` — 여기서는 기다린다.** `content_state` 가 절대
안 기다리는 것과 일부러 다르다. 사람이 손가락으로 누르고 화면을 보고 있는 요청이라
4초를 기다리는 것이 낡은 숫자를 보는 것보다 낫다(실측 1.4초). 앱 쪽 타임아웃도
이 요청만 20초다.

**가족 화면에도 칩이 뜬다.** 처음에는 귀가자만 보이게 하려 했는데 구조가 막는다 —
`content_state` 는 모든 수신자에게 똑같이 나가고, 노선도는 귀가자와 가족이 **같은
뷰**를 쓴다(`ContentView.swift` 가 그것을 일부러 지킨다). 가르는 값을 치를 이유가
아직 없어서 같이 보이게 뒀다.

## 오늘(오후) 새로 알게 된 함정

**시험이 통과하는데 기능이 안 된다.** 시험 환경에는 `TAGO_KEY` 가 없어서 조회가
즉시 빠져나간다. 그래서 91개가 전부 0.04초에 통과했고, `content_state` 가 9~13초
걸리는 것도 로컬 갱신이 값을 지우는 것도 **시험은 하나도 못 잡았다.** 둘 다 화면을
봐야 나왔다.

**`railway ssh` 가 사내망에서 막힌다.** 키를 등록해도 `Connection closed by
66.33.22.3 port 22` 다. 포트 22 자체는 열린다(`nc` 로 확인) — Railway 쪽이 닫는다.
배포 DB 를 그 길로 열 수 없다.

**배포 경로를 볼 다른 길이 있다.** 앱의 `-homecomingDumpRoute <id|이름>` 가 경로를
서버가 받는 형태 그대로 콘솔에 찍는다. 실기기에서 이렇게 부른다 — **`--` 로 인자를
갈라야 한다.** 안 그러면 `devicectl` 이 `-t` 로 읽는다.

```
xcrun devicectl device process launch --device <UDID> --console --terminate-existing \
  com.kona.homecoming2 -- -homecomingDumpRoute 퇴근길
```

**로컬 DB 의 경로를 사용자의 경로로 착각하지 말 것.** 로컬에는
`회사-집 (10구간)`·`회사-집` 가 있고 **`퇴근길` 은 배포 서버에만 있다.**
이 회차에서 그걸 착각해 잘못된 기둥(20573)을 근거로 한참 잘못 진단했다.

**재설치는 라이브 액티비티를 죽인다.** 그러면 앱 카드가 안 뜬다(카드는 액티비티를
그리는 것이다). 반대로 **앱 종료만으로는 액티비티가 안 죽는다** — 그 상태로
`-autoLiveHomecoming` 을 부르면 `coordinator.start()` 가 "이미 진행 중" 으로
건너뛰고 세션이 안 열린다. 깨끗이 하려면 `uninstall` → `install` → 기본값 재설정
(`homecoming.selectedRouteId`) → `-autoLiveHomecoming` 순서다.

**`xcrun simctl launch` 가 인자를 씹는 것을 또 봤다** (이번 회차에 세 번). 씹히면
앱이 배포 서버(HTTPS)로 붙어 `TLS 오류로 인해 보안 연결이 실패했습니다` 가 뜬다.
콘솔의 `[귀가마중] 토큰 주입됨` 으로 확인하고 재시도 루프로 감싼다.

**시뮬레이터를 스크롤할 수단이 없다.** 지도가 보이는 높이의 72% 를 먹어서 노선도가
아래로 밀리는데, 접근성 권한이 없어 창을 못 누른다. **화면 확인은 사람 눈이
필요하다** — 이 회차의 정렬 확인이 그래서 사용자 손을 탔다.

**두 대를 보려면 서버를 하나 더 띄운다.** 실자료는 배차 간격 때문에 같은 노선이
한 대일 때가 많다. `tago_arrival_rows` 만 가로채고 나머지는 진짜 서버 그대로 도는
것을 다른 포트에 띄우면 두 줄 칩을 확인할 수 있다(둘이 같은 DB 를 쓴다).
**확인이 끝나면 반드시 내린다** — 가짜 값을 실자료로 착각하기 쉽다.
