## 오늘(오후) 한 일

### 경기도 GBIS 가 열렸다

**TAGO 에는 "노선 하나로 그 노선 정류장 전부" 라는 호출이 없다.** 정류장을 주면
거기 오는 노선이 온다 — 방향이 반대다. 그래서 이름만 있을 때 어느 기둥인지 정할
근거가 없었다(풍산역은 기둥이 넷이고 999는 둘에만 선다).

경기도 GBIS 에는 그 호출이 있다. 공공데이터포털 **같은 키**를 쓰고 활용신청만
하면 된다(2026-08-27 승인, 오퍼레이션마다 일 1,000회 따로).

```
busstationservice/v2/getBusStationAroundListv2    좌표 → 주변 정류소(좌표 포함)
busstationservice/v2/getBusStationListv2          이름 → 정류소(좌표 포함)
busstationservice/v2/getBusStationViaRouteListv2  정류소 → 경유 노선
busrouteservice/v2/getBusRouteListv2              노선번호 → routeId
busrouteservice/v2/getBusRouteStationListv2       routeId → 경유정류소
busrouteservice/v2/getBusRouteLineListv2          routeId → 노선 형상(816점)
busarrivalservice/v2/getBusArrivalListv2          정류소 → 도착정보
```

**정류소 id 가 TAGO 와 같은 번호다.** TAGO `GGB219000638` = GBIS `219000638`.
접두사 `GGB` 만 붙는다(기둥 5개 표본 일치). **갈아타는 것이 아니라 덧붙일 수 있다.**

**방향이 순서로 갈린다.**
```
20753  999  seq 13  종점 신원중학교      ← 귀가 방향
58271  999  seq 78  종점 대화역(중)      ← 반대
```

**같은 정류소가 두 번 나오는 노선은 없었다** — 999 · 7770 · 7780 · 7790 등 7개에서
중복 0개. 그래서 `seq` 비교로 방향을 가려도 무너지지 않는다.

### 이름만으로 정류장을 정한다 (서버)

설계 [`specs/2026-08-27-stop-resolution-design.md`](superpowers/specs/2026-08-27-stop-resolution-design.md) ·
계획 [`plans/2026-08-27-stop-resolution.md`](superpowers/plans/2026-08-27-stop-resolution.md)

**새 엔드포인트를 안 만들었다.** `/bus/leg` 이 좌표 없이도 답하고, 응답에
`boarding`/`alighting` 후보를 싣는다. 옛 앱은 좌표를 늘 보내므로 동작이 그대로다.

```
GET /bus/leg?no=999&from=풍산역 버스정류장&to=위시티1,3단지
  → boarding  [20753 seq 13]        확정
    alighting [20796 seq 21, 20795 seq 70]   후보 둘
```

**후보를 하나로 안 줄인다.** 이름 매칭이 실패하면 좌표 근처로 폴백하던 안전망이
좌표 없는 길에는 없다. 억지로 하나를 고르면 그게 곧 조용히 틀린 값이 된다.

**좌표가 오면 그것이 답이다.** `위시티1.3단지` 가 길 양쪽에 있고 둘 다 방향
조건을 통과하는데, 사용자가 편집기에서 찍은 도착점이 갈랐다(5.0m 대 32.8m).
앱이 그 좌표를 **갖고만 있고 안 보내던 것**을 보내게 했다(`toLat`/`toLon`).

서울은 TOPIS 목록으로 같은 모양을 만들었다 — 새 호출이 없다.

실측(배포 서버):
```
999  승차 20753 seq 13 · 하차 20796           경기 / GBIS
163  승차 19132 seq 60 · 하차 14205 seq 64    서울 / TOPIS   저장된 승차점에서 2.1m
```

### 실기기에서 본 것 — 버그 둘

**`곧 도착` 일 때 숫자가 사라졌다.**
`busArrivalStopsText` 가 `stops > 0` 이라 0 을 걸렀다. 그런데 0 은 "없음" 이 아니라
**그 정류장에 지금 닿고 있다**는 뜻이다. 하필 뛸지 말지를 정해야 하는 순간에만
숫자가 없어졌다. 실측 — 163번 `staOrd 60 − sectOrd1 60 = 0`, `arrmsg1 = 곧 도착`.
이제 그대로 `곧 도착` 이라고 적는다. **실기기에서 확인했다.**

**heartbeat 첫 발화가 매번 걸러져 실효 간격이 4분이었다.**
120초 자고 일어나 "마지막 보고가 120초보다 오래됐나" 를 물었는데, 재는 시작점이
타이머보다 뒤라 119.x초로 읽혔다.
```
고치기 전   12:49:07 시작 · 12:51 건너뜀 · 12:53:08 첫 보고    4분
고친 뒤     13:11:45 시작 · 13:11:46 첫 보고 · 13:13:47        2분 1초
```
주석이 요구한 "노선도의 3분 문턱보다 짧게" 가 깨져 있었다 — 있으나 마나가 아니라
반대로 작동했다.

**서 있는 동안의 자동 갱신은 잘 돈다.** 33초 간격으로 값이 바뀌는 것을 로그로
확인했다(어제 고친 자리).

### 칩이 왜 없는지 말하게 했다

칩이 안 뜨는 것은 정상일 때가 많다(승차가 아직 멀다). 문제는 **고장일 때도 화면이
똑같다**는 것이다. 오늘 그것 때문에 원인을 못 가렸다 — 번호가 비었는지, 창 밖인지,
진행도가 튄 것인지.

`arrival_says()` 가 세 갈래를 각각 말한다. 이유가 바뀔 때만 찍는다.

`getBusStop` 에 11000~11999 를 전부 넣었다. **하나도 안 나온다.** TAGO 도시코드

### 시험이 진짜 DB 를 지우던 것

**오늘 이것으로 로컬 DB 의 `퇴근길` 이 날아갔다.**

```
DB_PATH = os.environ.get("HOMECOMING_DB", "Server/homecoming.sqlite")   ← 상대경로
```

import 할 때 한 번 정해지고 기본값이 상대경로다. `HOMECOMING_DB` 를 거는 시험이
일곱 중 셋뿐인데 **먼저 import 되는 `test_bus_arrival` 이 안 걸어서** 그쪽이 이겼다.

```
cd Server && python3 -m unittest discover   → Server/Server/homecoming.sqlite (유령 폴더)
python3 -m unittest discover -s Server      → 진짜 DB 를 지운다
```

**`rm -rf Server` 사고와 같은 뿌리다.** 그 사고도 이 유령 폴더를 치우려다 났다.

고친 것 — `default_db_path()` 로 절대경로, 시험 다섯에 가드, **가드가 빠지면
걸리는 시험 둘**. 표식 행을 넣고 양쪽에서 돌려 살아남는 것을 확인했다.

## 오늘 새로 알게 된 함정

**0 을 "없음" 으로 읽지 말 것.** `0정류장 전` 은 가장 중요한 값이다.

**같은 상수를 자는 시간과 거르는 문턱에 같이 쓰지 말 것.** 타이머가 재는 시작점이
언제나 조금 앞서서, 첫 발화가 매번 걸러진다. 실효 간격이 두 배가 된다.

**`railway up` 은 지금 디렉터리를 올린다.** `cd Server` 상태에서 쐈더니 `Server/`
가 루트로 올라갔다. 이번엔 경로를 전부 `__file__` 기준으로 잡아서 살았지만
운이었다. **저장소 루트에서 쏜다.**

**`--terminate-existing` 으로 앱을 재실행하면 세션이 닫힌다.** 앱이 죽는 것을
"그만" 으로 읽는 설계다. 실기기 확인 중에 그걸로 세션 하나를 끊었다.

**비교할 값의 출처를 확인할 것.** `26755m 남음` 을 28.4km 와 견줘 "진행도가 튀었다"
고 했는데, 28.4km 는 공개용 시험 경로(`commute-sample.json`)의 길이지 사용자
경로가 아니었다. 실제 경로는 실측 합계 ≈26,600m — **진행도는 안 튀었다.**
