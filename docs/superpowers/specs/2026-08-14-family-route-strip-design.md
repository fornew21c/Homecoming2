# 가족 화면의 노선도 — 설계

작성 2026-08-14 · 브랜치 `auth-session-token`

## 왜 하는가

가족이 앱을 열면 잠금화면과 **글자 하나 안 틀리게 같은 카드**가 나온다. 앱을 열
이유가 없다.

같은 것이 나오는 건 실수가 아니라 결정이었다 — `Shared/HomecomingViewParts.swift:3-6`
에 "같은 값을 다르게 그리면 어느 쪽이 맞는지 알 수 없으므로 그리는 코드를 하나로
둔다"고 적혀 있다. 이 설계는 그 결정을 **뒤집지 않는다.** 같은 값을 그대로 쓰되,
잠금화면이 자리가 없어서 못 하는 것을 앱에서 한다.

**목적은 하나다 — 아빠가 언제 오는지 가족이 안다.** 정확한 위치 추적이 아니다.
경로의 어디쯤 왔는지, 몇 정거장 남았는지가 보이면 된다.

**귀가자에게도 같은 것을 보여 준다.** 목적은 다르다 — 귀가자는 자기가 어디 있는지
알므로 위치가 필요 없다. 필요한 건 **"가족에게 지금 이렇게 보인다"는 확인**이다.
지금 귀가자 화면에는 "가족에게 전송" 한 줄뿐이라 가족 화면이 어떤 모습인지 알 길이
없다.

## 무엇을 만드나

**뷰 하나다.** 가족용 카드(`WatchingCard`)의 진행 바 자리에 **세로 노선도**를 넣고,
귀가자 화면은 같은 뷰를 그대로 쓴다. `Shared/HomecomingViewParts.swift` 의 조각들과
같은 자리에 산다.

```
┌─────────────────────────────────────────┐
│      ○ 출발                              │
│      │                                  │
│      ● 출발역.은행앞             │  지나온 구간: 진하게
│      │  버스 9분                         │
│      ● 환승로터리                         │
│      │                                  │
│      ● 서강대역                           │
│      ┃  지하철                            │
│      ◉ ← 지금 여기                        │  흰 점, 빛나는 테두리
│      ╎  31분 구간 · 12분 전 확인          │
│      ○ 풍산역                            │  남은 구간: 흐리게
│      ╎                                  │
│      ○ 아파트단지                      │
│      ╎  도보 3분                          │
│      ⌂ 집                                │
├─────────────────────────────────────────┤
│  🚇  지하철 · 풍산역까지 12분        23분  │
│      아빠가 오는 중              19:42 도착 │
└─────────────────────────────────────────┘
```

**노선도가 답하는 것은 "어디쯤"이고, 아래 줄이 답하는 것은 "언제"다.** 이 둘이
가족이 묻는 전부다.

지금 카드의 값은 하나도 안 버린다. 이동 수단 배지·카운트다운·도착 시각·`detail`
한 줄이 노선도 아래로 내려가고, 진행 바 자리를 노선도가 대신한다. 진행 바는
"28.4km 중 얼마"를 한 축으로 눌러 놓은 것이고, 노선도는 그걸 펴서 **정류장 이름을
붙여 준다.** 그게 유일한 차이다.

## 왜 지도가 아니라 노선도인가

진짜 지도(MapKit)를 검토하고 접었다.

**우리가 가진 건 정류장 8점이고 그 사이는 직선이다.** 이걸 지도에 올리면 한강을
가로지르는 선이 눈에 띈다. 지도는 "이게 정확한 위치"라고 말하는 매체라서, 부정확한
선을 올리면 거짓말이 된다. 노선도는 순서와 남은 개수만 말하겠다고 선언하는 매체라,
8점 직선이 **정확한 표현**이 된다.

마중 나가는 순간은 마지막 구간이다. 노선도는 "아파트단지 지남 → 다음 집"을 크게
보여 줄 수 있다. 28km 축척 지도에서 마지막 181m는 점 하나다.

부수 효과로 **좌표가 가족 폰에 한 바이트도 안 간다.** 노선도는 지리가 필요 없다.
"경로 위로만 보낼까, 실좌표를 보낼까"라는 질문 자체가 사라진다. MapKit 렌더링과
지도 타일 요청도 없다.

## 귀가자 화면

**같은 뷰를 그대로 쓴다.** 아래 한 줄까지 가족 화면과 글자 하나 안 틀리게 같다.

자기 폰에 "아빠가 오는 중"이라고 뜨는 건 어색하다. 그런데 그게 요점이다 — 귀가자가
보는 것은 자기 상태가 아니라 **가족에게 나가고 있는 그림**이다. 어색함을 없애려고
문구를 바꾸면 그 뜻이 사라진다. 알고 그대로 둔다.

**놓는 자리** — `statusCard` 안이 아니라 그 위, "내 귀가" 라벨 바로 아래에 별도
카드로 둔다. 귀가 중일 때만 나온다. `statusCard` 는 조종석이다(가족에게 보이는 이름,
추정 출처, 관측 보정, 전송 상태). 진단값과 공유되는 그림은 성격이 다르므로 섞지
않는다.

## 데이터가 어떻게 오나

### 새 고정값

귀가 중에 안 바뀌므로 갱신값이 아니라 `HomecomingAttributes` 의 고정값이다.

```swift
struct RouteShape: Codable, Hashable {
    struct Stop: Codable, Hashable {
        var name: String      // "풍산역"
        var mode: String      // 여기까지 오는 수단: walk / bus / subway
        var meters: Int       // 여기까지 오는 거리
        var seconds: Int      // 여기까지 걸리는 시간
        var waitSeconds: Int  // 여기서 갈아타며 기다리는 시간 (없으면 0)
    }
    var stops: [Stop]         // 마지막이 집
}
```

`HomecomingAttributes` 에 `var routeShape: RouteShape?` 를 더한다. **옵셔널이다** —
경로 없이 시작한 귀가와, 이 변경 전에 시작된 액티비티가 안 깨진다.

`mode` 는 **경로가 쓰는 낱말 그대로**다(`walk` / `bus` / `subway`). 갱신값의
`Transport` 열거형과 별개이고 서로 변환하지 않는다. 경로의 낱말은 구간을 설명하고
`Transport` 는 지금 무엇을 타고 있는지를 말하므로, 둘을 잇는 순간 노선도가 갱신값에
매이게 된다. 노선도가 갱신값을 안 건드린다는 성질이 이 분리에서 나온다. 아이콘은
`mode` 를 SF Symbol 이름으로 옮기는 표 하나로 정한다.

### 접는 규칙은 서버에만 산다

가족 액티비티는 **서버**가 시작하고(`start_activities()`), 귀가자 액티비티는 **앱**이
시작한다. 그래서 앱이 자기 경로를 직접 접게 두면 **같은 규칙이 파이썬과 스위프트에
두 벌** 생긴다. 어긋나면 귀가자와 가족이 다른 노선도를 본다.

오늘 세 번 겪은 사고가 정확히 이것이다 — *"앱이 만드는 시작 카드는 서버가 낼 값과
같아야 한다. 앱이 짐작하고 서버가 덮어쓰면 카드가 튄다."*

**세션 응답으로는 늦다.** 앱은 `activity.start()` 를 `openSession()` 보다 **먼저**
부른다(`HomecomingCoordinator.swift:271` 과 `288`). 액티비티 고정값은 그 순간 굳으므로
세션 응답이 와도 넣을 자리가 없다.

**그런데 이 문제는 이미 풀려 있다.** `GET /route` 의 `summary()` 가 정확히 같은
이유로 서버에서 접어 준다 — 주석에 이렇게 적혀 있다:

> 앱이 귀가 시작 순간의 카드를 직접 만든다. 서버 응답을 기다리지 않는다. 그런데
> 앱은 경로의 구간을 모르니, 없으면 MapKit 이 준 자동차 경로를 쓰게 된다 — 걸어서
> 역까지 가는 첫 6분에 카드가 "차량 탑승" 으로 떴다.

`totalMeters`·`firstTransport`·`firstDetail` 이 그렇게 온다. **`stops` 도 같은 자리에
넣는다.** 앱은 `RouteStore` 캐시에서 귀가 시작 시점에 이미 들고 있으므로 추가 요청이
없고, 순서 문제도 없다. 접는 규칙은 여전히 파이썬 한 곳이다.

`GET /route/{id}` 응답에도 같은 값을 넣는다 — 목록과 상세가 다른 말을 하면 안 된다.

### 접는 함수

`Server/homecoming_server.py` 에 `route_stops(legs)` 를 하나 두고 **세 곳이 함께
쓴다** — `attributes_for()` (가족 액티비티), `GET /route` 의 `summary()` (귀가자
액티비티), `GET /route/{id}` (상세). `route_length()` · `transport_of()` ·
`leg_sentence()` 가 이미 사는 자리 옆이다.

**접는 규칙은 하나다 — `mode == "wait"` 구간은 점을 만들지 않고 앞 정류장의
`waitSeconds` 로 붙는다.** 대기는 앞 구간과 같은 자리라 점을 따로 찍으면 노선도에
같은 자리가 두 번 나온다. 그래서 10구간이 **점 7개**가 된다.

**출발점은 `stops` 에 없다.** 정류장은 "그 구간이 끝나는 자리"라서 출발점은 어느
구간의 끝도 아니다. 노선도에는 맨 위에 이름 없는 점으로 그리므로 화면에는 자리가
8개 보인다 — 목록의 7개와 그림의 8개가 다른 것은 이 때문이다.

실제 경로(`Tools/routes/commute-sample.json`)로 확인한 결과:

| 구간 | mode | toName | meters | 노선도 |
|---|---|---|---|---|
| 0 | walk | 출발역.은행앞 | 445 | 점 |
| 1 | wait | — | — | 앞 점의 waitSeconds 180 |
| 2 | bus | 환승로터리 | 5,357 | 점 |
| 3 | walk | 서강대역 | 664 | 점 |
| 4 | wait | — | — | 앞 점의 waitSeconds 240 |
| 5 | subway | 풍산역 | 18,683 | 점 |
| 6 | walk | 풍산역 정류장 | 78 | 점 |
| 7 | wait | — | — | 앞 점의 waitSeconds 120 |
| 8 | bus | 아파트단지 | 2,950 | 점 |
| 9 | walk | 집 | 181 | 점 |

구간 `meters` 의 합이 28,358m — 세션의 `totalMeters` 와 같다. 점 위치 계산이 이
일치에 기댄다.

**출발점에는 이름이 없다.** 경로에 origin 이름을 저장하지 않는다(`RouteDraft` 에
그 칸이 없다). 첫 점 위에 "출발"이라고만 쓴다.

### 갱신값은 한 글자도 안 건드린다

`ContentState` 에 필드가 늘지 않는다. 그래서 서버의 갱신 푸시 코드, 위젯, 잠금화면,
다이내믹 아일랜드, e2e 도구가 전부 그대로다.

**이게 이 설계의 핵심 성질이다.** 오늘 세 번 겪은 "앱이 짐작한 값과 서버가 낸 값이
어긋나 카드가 튄다" 사고가 여기서는 일어날 수 없다 — 나르는 값이 안 늘었으니까.

### 점을 어디에 찍나

순수 함수 하나. 새 데이터가 아니라 **이미 있는 값**으로 계산한다.

```
지나온거리 = totalMeters - remainingMeters
구간별 meters 를 누적하며 지나온거리가 드는 구간을 찾는다
그 구간 안의 비율 = (지나온거리 - 구간시작누적) / 구간meters
```

대기 구간은 점이 아니므로 계산에서 아예 빠진다 — 실제로 대기 중엔 안 움직이는 것과
맞는다.

## 위치 보고가 끊길 때

지하철 구간에서 위치 보고가 31분 끊긴다. **점은 마지막으로 확인된 자리에 그대로
두고 흐리게 만들며, 옆에 "12분 전 확인"을 붙인다.**

예상 위치로 이어서 움직이는 안을 검토하고 버렸다. 지연되면 점이 집에 먼저 도착해
있는 거짓말을 한다. 아는 것만 말한다는 이 프로젝트의 원칙 그대로다.

아래 카운트다운은 푸시 없이도 시스템이 정확하게 줄인다(`CountdownText` 주석 참고).
그래서 **"어디쯤"은 멈춰도 "언제"는 안 멈춘다.** 이게 노선도와 아래 줄을 함께 두는
이유이기도 하다.

## 어디가 위험한가

**정류장 이름이 길다.** `출발역.은행앞` 이 한 줄에 안 들어간다. 오늘 이미
데인 자리다(`306e036 잠금화면과 아일랜드에서 글씨가 잘렸다`). 줄임표와 최소 축소
배율을 처음부터 넣는다.

**세로로 길다.** 점 7개면 카드 하나 높이를 넘는다. 스크롤을 만들지 않고 **접는다.**
규칙은 이렇다 — 항상 보이는 것은 **출발점, 현재 구간의 앞뒤 점, 집** 이다. 그 사이에
낀 지나온 점이 2개를 넘으면 `⋯ N곳 지남` 한 줄로 접는다. 즉 화면에 점이 최대 4개와
접힘 한 줄이 보인다. 접힌 줄은 누를 수 없다 — 펼치기를 만들면 이 화면이 목록이 되고,
가족이 한눈에 읽는다는 목적이 흐려진다.

**페이로드가 넘칠 수 있다.** 10구간이면 600바이트 남짓이라 APNs 4KB 한도에 여유가
많다. 그러나 구간 수를 정하는 건 사용자다. 서버가 attributes JSON 크기를 재고 3KB를
넘으면 `routeShape` 를 빼고 보낸다(가족은 지금 카드를 본다). **조용히 빼지 않고
로그에 남긴다** — 오늘 가장 비쌌던 교훈이 계기판이 거짓말한 것이었다.

**귀가 중에 경로를 고치면 노선도는 옛것이다.** 액티비티의 고정값은 불변이라 바꿀 수
없다. 그런데 아래 `detail` 줄은 서버가 새 경로로 말하므로 노선도와 아래 줄이 어긋날
수 있다. 귀가 중에 경로를 고치는 건 드무니 받아들이되, **아는 채로 받아들인다.**

**경로 목록을 못 받았으면 귀가자 노선도가 없다.** `RouteStore` 캐시가 비어 있으면
`stops` 도 없다. 그런데 그 경우 지금도 `firstTransport` · `totalMeters` 가 없어서
카드가 MapKit 폴백으로 뜬다 — 새 실패 모드가 아니라 **이미 있는 실패 모드에 하나 더
얹히는 것**이다. `routeShape` 가 nil 이면 지금 카드가 그대로 나온다.

**옛 앱과 새 서버가 섞인다.** 서버가 `stops` 를 보내도 옛 앱은 모르는 키라 무시한다.
새 앱이 옛 서버를 보면 `stops` 가 없어 카드로 폴백한다. 양쪽 다 안 깨진다.

**위젯 타겟도 같은 attributes 를 디코드한다.** `routeShape` 를 쓰지 않지만 파싱은
한다. 옵셔널이라 옛 액티비티도 안 깨진다.

## 검토하고 접은 안

**진짜 지도(MapKit)** — 위 "왜 지도가 아니라 노선도인가" 참고.

**압축 폴리라인을 페이로드에** — 254점을 encoded polyline 으로 ~1.5KB 까지 줄여 실을
수 있다. 진짜 길 모양이 나온다. 그러나 경로 길이를 정하는 건 사용자이고, 넘치면
액티비티가 아예 시작을 못 한다 — 가장 나쁜 실패다. 파이썬 인코더와 스위프트 디코더를
새로 짜야 하는 것도 오늘 이중 URL 인코딩으로 데인 것과 같은 종류의 함정이다.

**가족 앱이 서버에서 경로를 받아온다** — `GET /route/{id}` 로 254점을 받는다. 지금
서버는 `WHERE id = ? AND account_id = ?` 로 막고 있고 `/session/{id}` 도 "남의
세션이면 있는지 없는지도 알려 주지 않는다"고 못 박아 뒀다. **"지켜보는 사람은 그
경로를 볼 수 있다"는 새 권한을 뚫어야 한다.** 일부러 좁혀 놓은 자리를 넓히는 일이라
값이 비싸고, 오프라인 폴백도 따로 만들어야 한다. 노선도에는 254점이 필요 없으므로
이 값을 치를 이유가 없다.

**배달앱처럼 앱이 서버를 폴링** — 통로를 바꿔도 원본이 안 촘촘하다. 귀가자 폰은
`distanceFilter = 150` 으로 150m마다 보고하고(84분 백그라운드 추적의 배터리와 맞바꾼
값이다), 지하철 구간은 신호가 없어 아예 안 보낸다. 폴링을 아무리 자주 해도 새 값이
없다. 채널 문제가 아니라 신호 문제다. 게다가 **iOS 가 84분 동안 백그라운드 위치를
계속 주는지 자체가 아직 확인 안 됐다** — 그 답을 보기 전에 촘촘하게 만드는 건 순서가
뒤집힌 것이다.

## 어떻게 확인하나

**점 찍는 함수가 순수 함수라 시험이 싸다.** progress 0, progress 1, 각 구간 경계값,
대기 구간이 낀 자리, 구간 하나짜리 경로, `totalMeters == 0` 인 경우.

**`CommuteSimulator` 로 재생.** progress 0→1 을 돌려 점이 정류장 순서대로 지나가는지
눈으로 본다.

**폴백 확인.** `routeShape` 가 nil 이면 지금 카드가 그대로 나오는지.

**잘림 확인.** `출발역.은행앞` 처럼 긴 이름과, 구간이 많아 접히는 경우.

**두 화면이 같은지.** 귀가자 폰과 가족 폰의 노선도가 **글자 하나 안 틀리게 같아야
한다.** 다르면 접는 규칙이 두 벌이 됐다는 뜻이다. 이게 이 작업의 회귀 시험이다.

**실기기.** 페어링된 두 폰(`f9bd0a58` 귀가자, `a06b1002` 가족)으로 세션을 시작해
양쪽 앱에서 노선도가 뜨고 서로 같은지 나란히 놓고 본다.
