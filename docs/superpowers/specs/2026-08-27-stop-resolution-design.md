# 이름만으로 정류장을 정한다 — 경로 세팅의 허들 낮추기

2026-08-27 · **설계.** 구현 전이다

## 문제

경로 하나를 만드는 데 **입력이 25번**이다(`퇴근길`, 구간 7개 기준).

```
경로 이름 · 출발지 찾기                    2
구간마다 : 수단 · 소요분 · 도착지 지도에서 찍기   7 × 3
버스 구간의 노선번호                        2
```

제일 무거운 것이 **지도에서 정류장 찍기**다. 확대해서 맞는 기둥을 눌러야 하는데,
같은 이름의 기둥이 여럿이다. 풍산역은 넷이고 999는 그중 둘에만 선다. **틀리게
찍어도 저장할 때 아무 표시가 없고**, 나중에 도착 칩이 안 뜨는 것으로만 드러난다.

궁극적으로 하려는 것은 **길찾기 앱 캡처를 올리면 채워지는 것**이다. 그런데 캡처에는
글자만 있고 좌표가 없다. `풍산역` 이라는 글자에서 기둥을 정할 근거가 필요하다.

이 문서는 **그 근거를 만드는 1단계**다. 캡처는 다루지 않는다.

## 오늘 열린 것 (2026-08-27, 실측)

경기도 GBIS API 를 활용신청했다. 공공데이터포털 같은 키를 그대로 쓴다.

```
busstationservice/v2/getBusStationAroundListv2   좌표 → 주변 정류소(좌표 포함)
busstationservice/v2/getBusStationListv2         이름 → 정류소(좌표 포함)
busstationservice/v2/getBusStationViaRouteListv2 정류소 → 경유 노선
busrouteservice/v2/getBusRouteListv2             노선번호 → routeId
busrouteservice/v2/getBusRouteStationListv2      routeId → 경유정류소
busrouteservice/v2/getBusRouteLineListv2         routeId → 노선 형상
busarrivalservice/v2/getBusArrivalListv2         정류소 → 도착정보
```

**오퍼레이션마다 일 1,000회가 따로 잡힌다.** 지금 TAGO 한 계정에 몰려 있던 압박이
갈라진다.

### 이것이 바꾸는 것

**경유정류소 목록이 기둥 단위로, 좌표까지 온다.** 999(routeId 218000111) 92개:

```
seq  11  219000609  20572  저동중고교          (37.66977, 126.77825)
seq  12  219001059  58261  밤가시7.8단지.광림교회  (37.67127, 126.78232)
seq  13  219000638  20753  풍산역             (37.67315, 126.78722)
seq  14  219000605  20576  애니골입구          (37.67435, 126.79197)
```

**정류소 id 가 TAGO 와 같은 번호다.** TAGO `GGB219000638` = GBIS `219000638`.
접두사 `GGB` 만 붙는다(기둥 5개 표본 일치). 갈아타는 것이 아니라 **덧붙일 수 있다.**

**방향이 순서로 갈린다.** 길 양쪽 두 기둥이 같은 노선인데:

```
20753   999  seq 13  종점 신원중학교      ← 귀가 방향
58271   999  seq 78  종점 대화역(중)      ← 반대
```

경유노선 조회의 `staOrder` 와 경유정류소 목록의 `stationSeq` 는 같은 값이다
(풍산역 20753 에서 둘 다 13). 아래에서는 `seq` 로 적는다.

**같은 정류소가 두 번 나오는 노선은 없었다.** 999 · 7770 · 7780 · 7790 등 7개
노선에서 중복 0개, `turnYn=Y` 는 회차점 표시 하나뿐이다. 그래서 `seq` 비교로
방향을 가려도 무너지지 않는다.

## 무엇을 바꾸나

**새 엔드포인트를 만들지 않는다.** `/bus/leg` 가 이미 이 일을 한다.

```
지금  GET /bus/leg?no=999&from=<승차이름>&to=<하차이름>&fromLat=…&fromLon=…
      → { points: [...] }

바뀜  GET /bus/leg?no=999&from=<승차이름>&to=<하차이름>       ← 좌표 없이도 답한다
      → { points: [...],
          boarding:  [ { id, no, name, lat, lon, seq } ],     ← 후보 목록
          alighting: [ { ... } ] }
```

**기존 앱은 좌표를 계속 보내므로 동작이 그대로다.** 저장소 규칙 `와이어 프로토콜은
추가만 한다` 에 맞는다.

### 후보를 하나로 줄이지 않는다

이름은 세 갈래로 갈린다 — 사용자가 적은 것(`풍산역 버스정류장`), 자료의 것
(`풍산역`), 길찾기 앱의 것. `n_eq()` 가 점·쉼표·공백은 지우지만 `버스정류장` 같은
접미어는 못 지운다.

**지금 코드에는 안전망이 있다.** `bus_leg_waypoints` 는 이름 매칭이 실패하면 좌표
근처 정류장으로 폴백한다(`homecoming_server.py:921`). 좌표를 안 받는 길에는 그
폴백이 없다.

그래서 **확실할 때만 하나, 애매하면 목록**을 돌려준다. 편집기가 고르게 한다. 이
저장소의 판단 — *틀린 값을 그리는 것보다 안 그리는 것이 낫다* — 의 연장이다.

`toName` 은 원래 표시용 자유 문구다(편집기 힌트가 `카드에 보일 이름` 이고
`163번 대기` 같은 것도 들어간다). **못 찾는 것이 정상인 경우가 있다.** 실패를
오류로 취급하지 않는다 — `points: []` 가 이미 "그릴 것이 없다" 로 쓰이는 것과 같다.

## 어떻게 정하나

```
1. 노선번호로 후보 노선을 받는다          999 → 3개(고양 · 수원용인화성 · N999)
2. 두 이름이 다 들어 있는 노선만 남긴다    ← 지금 코드가 쓰는 방법 그대로
3. 그 노선의 경유정류소에서 두 이름을 찾는다
4. 승차 seq < 하차 seq 인 쌍만 받아들인다  ← 방향
5. 남은 것이 하나면 확정, 여럿이면 후보로 돌려준다
```

**`확정` 의 뜻** — 정규화 완전일치가 정확히 하나일 때만이다. 부분일치로 찾았거나
둘 이상 남으면 확정이 아니고, 후보를 순서대로 돌려준다. 앱은 확정일 때만 자동으로
채우고, 아니면 사람에게 고르게 한다.

이름 대조는 `n_eq()` 로 정규화한 뒤 **완전일치 먼저, 없으면 부분일치**다.
`stops_by_name` 이 이미 같은 규율을 쓴다.

## 두 지역

| | 서울 | 경기 |
|---|---|---|
| 노선번호 → 노선 id | `seoul-routes.json` (구워 둠) | `getBusRouteListv2` |
| 노선 → 정류장 목록 | `getArrInfoByRouteAll` (TOPIS) | `getBusRouteStationListv2` |
| 정류장 좌표 | `seoul-stops.json` (구워 둠) | 응답에 포함 |

서울 쪽은 이미 `seoul_arrival_items_cached` 가 그 목록을 받고 있다. **새로 붙일
호출이 없다.**

## 열어 둔 것

**서울의 정류장 목록은 도착정보 호출로 얻는다.** 경기의 경유정류소 목록과 성격이
다르다 — 차가 안 다니는 시간에 비는지 아직 안 재 봤다. 구현 중에 심야 노선으로
확인한다. 비면 서울은 그 시간대에 후보를 못 준다(빈 목록이지 틀린 값은 아니다).

## 캐시와 한도

- 노선번호 → routeId : 영구. 바뀌지 않는다
- routeId → 경유정류소 : 영구. 정류소 자리는 바뀌지 않는다
- 첫 조회 비용 : 노선 후보 1회 + 후보마다 경유정류소 1회 (999 는 최대 4회)

`bus_route_stop_names` 가 이미 `_bus_route_stops` 로 같은 캐시를 한다.

## 앱도 같이 고친다

**서버만 고치면 화면이 안 바뀐다.** `points[0]` 은 정류장 자료가 아니라 **직전
구간의 도착 좌표**다(`RouteTracer.swift:224`, `cursor = from` 에서 시작해 `to` 로
끝난다). 도착 조회가 그 점을 쓴다.

그래서 `boarding` 을 받아 이득을 보려면 **앱이 직전 구간의 좌표를 그 값으로
바꿔야** 한다. 이 저장소가 여러 번 당한 모양이다 — 시험은 다 통과하고 화면만 빈다.

## 시험

`Server/test_bus_route_stops.py` 옆에 붙인다. GBIS 응답을 고정해 두고 —

- `퇴근길` 의 999 구간이 **20753** 을 집는다 (정답을 안다)
- 반대 방향 **58271** 을 집으면 실패다
- `위시티1,3단지`(쉼표)로 물어도 `위시티1.3단지`(점)를 찾는다
- 이름이 애매하면 후보를 **여럿** 돌려준다. 하나로 줄이지 않는다
- `풍산역 버스정류장` 처럼 접미어가 붙어도 찾는다
- 좌표를 함께 보내면 지금과 **똑같이** 답한다 (기존 동작 보존)

**시험만으로는 안 된다.** 시험 환경에 키가 없어 조회가 즉시 빠져나간다. 실제
`퇴근길` 로 서버를 불러 20753 이 나오는지 봐야 한다.

## 범위 밖

- **캡처에서 글자 뽑기** — 2단계
- **편집기에 채워 넣기** — 3단계
- **노선 형상으로 선 그리기** — `getBusRouteLineListv2` 가 999에 816점을 준다.
  지금은 정류장을 직선으로 잇는다. **얼마나 나은지 재 보기 전에는 안 바꾼다**
- **경기 도착정보를 GBIS 로 옮기기** — 지금 TAGO 로 잘 되고 있다. 기둥이 정확히
  저장되면 더 그렇다
- **`BUS_SGG` 에 서울 넣기** — 저장된 163 구간에서 실제 정류장이 최대 124m 밖에
  안 벌어진다. 이탈 문턱 1,000m 의 8분의 1이라 이득이 없다
