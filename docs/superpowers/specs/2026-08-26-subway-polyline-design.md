# 지하철 구간을 실제 노선 모양으로 그린다 — 설계

2026-08-26

## 왜

지하철 구간은 **두 역 좌표를 잇는 직선**이다. `RouteTracer.line()` 이 `mode == .subway`
면 도로 경로를 묻지 않고 `straight(from:to:)` 로 200m 간격 보간을 만든다. 지하철은
도로를 따르지 않으니 자동차 경로를 물으면 엉뚱한 길이 나오기 때문이다.

그런데 **실제 노선은 직선이 아니다.** 서강대 → 풍산은 경의중앙선이 크게 휘어 도는
구간이고, 저장된 직선과 실제 선로가 1km 넘게 벌어진다.

2026-08-25 실주행에서 그 대가를 치렀다.

```
18:09:38  경로 이탈 1105m        ← 이탈 문턱 1,000m 를 105m 넘겼다
…                               복귀 로그 없음
18:48:39  세션 종료 (arrived)    ← 39분을 이탈 상태로 돌았다
```

이탈이 부른 것이 셋이다.

- 남은거리가 11,668m → 8,251m 로 한 번에 줄었다(경로 거리 → 집까지 직선거리)
- 도착예정이 앞당겨져 가족이 **도착한 줄 알았다**
- 지도의 지나온/남은 색 분리가 그 자리에서 멈췄다

뒤의 둘은 이미 고쳤다(`aa0ace2`, `d3e6e15`). 이 문서는 **원인**을 고친다.

18:12 실기기 캡처가 그림으로 보여 준다 — 파란 직선이 고양 상공을 가로지르고
귀가자 점은 그 아래 덕양구에 있다. 선이 틀렸지 사람이 틀린 게 아니다.

## 무엇을

역과 역 사이를 잇는 **꺾은선**으로 바꾼다. 서강대 → 홍대입구 → 가좌 → DMC → …
→ 풍산. 역 사이는 여전히 직선이지만 그 길이가 짧아 벌어짐이 수십~수백 m 로 준다.

**실제 선로 곡선까지 가지 않는다.** 이 앱이 그 정밀도로 하는 판단이 없다 — 이탈
판정도 지도 그림도 꺾은선이면 충분하다. 곡선 자료(선형 GIS)는 무겁고 형식·라이선스를
따로 봐야 한다.

## 자료

[전국도시철도역사정보표준데이터](https://www.data.go.kr/data/15013205/standard.do) —
[레일포털](https://data.kric.go.kr/rips/M_01_01/detail.do?id=32) 에서 XLSX 로 받는다.
**무료 · 이용허락 제한 없음 · 키 불필요.**

제공 항목: 역번호, 역사명, 노선번호, 노선명, 영문·한자명, 환승역 여부, 환승 노선,
**위도·경도**, 운영기관명, 도로명주소, 전화번호, 데이터기준일자.

### 왜 런타임 API 가 아니라 구워 두는가

버스는 런타임에 공공데이터를 부른다. 그 대가를 알고 있다 — 일일 한도 1,000회,
사내망 TLS(`CERTIFICATE_VERIFY_FAILED`), 응답 지연, 자료 없는 지역.

역 정보는 **자주 안 바뀐다.** 그 값을 매번 물어 위 대가를 치를 이유가 없다. 이미
같은 판단을 한 자료가 있다 — `Server/data/seoul-stops.json`(정류소 11,239건).

### 자료를 받아 확인했다 (2026-08-26)

파일은 이 주소로 받힌다 — 상세 페이지의 버튼이 가리키는 주소다.

```
https://data.kric.go.kr/rips/dataset/download.file?type=filedata&id=32&operation=1
```

313KB · 1,099행 · 51개 노선 · **좌표 빠진 행 0개.** 경의중앙선 51역, 5호선 56역,
2호선 50역으로 온전하다.

**XLSX 를 위치로 읽으면 안 된다.** 빈 칸을 건너뛰는 형식이라 열이 밀린다. 처음
그렇게 읽고 "좌표 없는 행이 661개" 라는 값을 얻었는데 사실이 아니었다. 셀 주소
(`A`·`B`·`J`·`K`)로 읽어야 한다.

### 역번호는 노선 전체가 아니라 **블록 안에서** 순서다

이게 원래 가정이었고, 재 보니 반만 맞았다. 노선 전체를 역번호로 세우면 경의중앙선의
비(`L순서/L최근접`)가 **1.417** 로 문턱을 넘는다. 지선과 옛 코드 블록 때문이다.

```
1201–1220  중랑 ~ 지평            ← 중앙선
1251–1252  서울역(경의선) · 신촌   ← 서울역 지선
1261–1286  효창공원앞 ~ 운천       ← 경의선 본선
1953       대곡                  ← 홀로 떨어진 코드
```

그런데 **한 구간은 한 블록 안에 있다.** 서강대(1263) → 풍산(1274) 사이를 역번호로
고르면 이렇게 나온다.

```
서강대 → 홍대입구 → 가좌 → 디지털미디어시티 → 수색 → 한국항공대
      → 강매 → 행신 → 능곡 → 곡산 → 백마 → 풍산
```

역 사이 간격이 527m ~ 3,456m 로 고르다. 되돌아가는 곳이 없다.

**그래서 검증을 노선 단위가 아니라 구간 단위로 한다.** 두 역 사이를 고른 뒤
이웃 간격을 보고, 블록이 다르면(간격이 터무니없이 크면) 그 구간은 **폴백한다.**
노선 전체를 세울 필요가 없다.

### 얼마나 좋아지는가 — 실측

```
직선(서강대→풍산)          18.7km
역을 거치는 꺾은선          19.5km

직선이 실제 노선에서 가장 멀리 벌어지는 곳   1,994m  (능곡역)
그날 기록된 벌어짐                        1,105m
이탈 문턱                                1,000m
```

**직선의 최대 벌어짐이 문턱의 두 배다.** 그날 1,105m 가 왜 났는지가 이 값으로
설명된다. 꺾은선으로 바꾸면 벌어짐이 역 사이 간격(최대 3,456m)의 절반 아래로
떨어진다 — 문턱을 건드릴 이유가 없어진다.

## 구성

### 1. `Tools/subway-lines.py` — 굽는 도구

내려받은 XLSX 의 **경로를 인자로 받아** `Server/data/subway-lines.json` 을 만든다.

```
python3 Tools/subway-lines.py ~/Downloads/전국도시철도역사정보표준데이터.xlsx
```

도구가 직접 내려받지 않는다. 레일포털의 파일 주소가 안정적인지 확인하지 못했고,
확인 안 된 주소를 코드에 박으면 어느 날 조용히 빈 파일이 된다. 자료는 사람이 한 번
받는다 — 역 정보는 자주 안 바뀐다.

```json
{
  "<노선번호>": {
    "이름": "경의중앙선",
    "역": [{"번호": "K314", "이름": "서강대", "lat": 37.5511, "lon": 126.9380}, …]
  }
}
```

**노선명이 아니라 노선번호로 키를 잡는다.** `1호선` 은 서울에도 부산에도 있다.
이름으로 묶으면 두 도시의 역이 한 노선에 섞이고, 그러면 사이 역을 세는 순간 엉뚱한
좌표가 나온다.

- 노선별로 **역번호 순 정렬** (블록을 넘는 순서는 보장하지 않는다 — 위 참고)
- 전국을 다 넣는다. 수도권만 거르는 필터가 오히려 실수를 만든다 — `수도권` 의 경계를
  코드가 정해야 하고, 경의중앙선처럼 서울과 경기를 넘나드는 노선에서 그 판단이 어긋난다.
  (크기는 굽고 나서 잰다. 지금 짐작하지 않는다)
- XLSX 는 **표준 라이브러리로 읽는다**(`zipfile` + `xml.etree`). 이 저장소는 의존성을
  안 쓴다 — 서버도 도구도 그 방침이다
- 노선을 거르지 않는다. **순서 판단은 굽는 쪽이 아니라 구간을 고르는 쪽**(서버)에서
  한다 — 노선 전체가 한 줄로 안 서는 것이 정상이기 때문이다

멱등하다. 다시 돌리면 같은 파일이 나온다.

### 2. 서버 — `GET /subway/leg?from=<이름>&to=<이름>`

두 역이 **함께 있는 노선**을 찾아 그 사이 역 좌표를 순서대로 돌려준다.

```json
{"line": "경의중앙선", "stops": [{"name":"서강대","lat":…,"lon":…}, …]}
```

- 여러 노선에 둘 다 있으면 **사이 역 수가 가장 적은** 노선을 쓴다(직통)
- **고른 구간의 이웃 간격을 본다.** 블록이 다르면 그 사이에 터무니없는 간격이 생긴다
  (경의중앙선에서 지선을 넘으면 58km 가 나온다). 문턱을 넘으면 빈 결과를 준다 —
  틀린 폴리라인은 직선보다 나쁘다. 문턱 값은 자료의 역 간격 분포를 보고 정한다
- 방향은 `from` → `to` 순으로 맞춘다
- 못 찾으면 `{"stops": []}` — 오류가 아니다
- **환승 없는 한 구간만 다룬다.** 경로의 지하철 구간 하나가 곧 한 노선이라는 전제이고,
  지금 경로 만들기가 그렇게 되어 있다(구간마다 도착역을 고른다)

`GET /bus/leg` 옆자리에 같은 모양으로 둔다.

### 3. 앱 — `RouteTracer`

```swift
if mode == .subway {
    return straight(from: from, to: to)   // ← 여기
}
```

`subwayWaypoints` 클로저를 끼운다. `busWaypoints` 와 같은 모양이라 배선이 이미 있다.

- 받은 역 좌표들을 순서대로 잇고, 구간마다 `subwaySpacing`(200m)으로 보간한다
- 첫 역·끝 역은 요청한 좌표로 맞춘다(`ending(_:at:)` 과 같은 이유 — 구간 사이에
  틈이 생기면 다음 구간이 다른 자리에서 시작한다)
- **못 받으면 지금처럼 직선을 그리고 그 사실을 남긴다.** `Plotted` 에
  `subwayFallbacks` 를 더해 편집기가 노선 이름을 적어 준다. 버스가 이미 그렇게 한다
  (`busFallbacks`) — 조용한 폴백은 만들지 않는다

### 4. 이름 맞추기

앱의 경로는 `서강대학교`·`풍산역` 인데 자료의 역사명은 `서강대`·`풍산` 일 수 있다.

- 정규화: 공백·가운뎃점 제거, 끝의 `역` 떼기
- 정규화해서 같은 것을 먼저 쓰고, 없으면 **포함하는 것**을 쓴다
- 그래도 못 찾으면 폴백. **짐작해서 엉뚱한 역을 넣지 않는다** — 틀린 폴리라인은
  직선보다 나쁘다(직선은 최소한 틀린 줄 안다)

버스의 `stops_by_name` 이 같은 문제를 같은 방법으로 풀었다(`애니골입구` →
`약산마을.애니골입구`).

## 검증

**성적표는 하나다.** 어제 트레이스로 서강대 → 풍산 구간에서 저장된 폴리라인과
실제 이동의 **최대 벌어짐**을 잰다.

```
직선의 최대 벌어짐    1,994m   ← 자료로 이미 쟀다 (능곡역)
그날 기록된 값        1,105m
목표                 < 1,000m  (이탈 문턱)
```

**결과 (2026-08-26).** 시뮬레이터에서 경로를 다시 만들어 쟀다.

```
저장된 지하철 좌표열      96점 · 20.0km   (직선일 때 18.7km)
실제 역들이 그 선에서      64m
직선이었다면            1,998m
이탈 문턱              1,000m
```

**1,998m → 64m.** 문턱의 두 배에서 16분의 1로 내려갔다. 문턱을 건드릴 이유가 없다.

`Tools/verify-progress-sync.py` 가 앱 원본을 컴파일해 견주는 것과 같은 방식으로,
굽힌 좌표열과 실주행 좌표를 견주는 스크립트를 둔다.

서버 시험 셋(`Server/test_subway_leg.py`):

- 두 역이 같은 노선에 있으면 사이 역들을 순서대로 준다
- `from`/`to` 순서가 뒤집혀 있어도 방향을 맞춘다
- 없는 역이면 빈 결과다 (오류가 아니다)

굽는 도구 시험 하나: 역번호 순서 검증이 실제로 걸러내는지.

## 안 하는 것

- **실제 선로 곡선.** 위 "무엇을" 참고
- **환승을 넘는 구간.** 경로 만들기가 구간마다 도착역을 고르는 구조라 필요 없다
- **실주행 GPS 로 경로 고치기.** 자료 출처가 필요 없다는 장점이 있지만, 첫 귀가는
  여전히 직선이라 그때 오판이 남는다. 이 자료가 있으면 첫 번부터 맞다. 나중에 이
  위에 얹을 수는 있다
- **이탈 문턱 조정.** 원인이 사라지면 문턱을 건드릴 이유가 없다. 고친 뒤 다시 재서
  그때도 벌어지면 그때 정한다
