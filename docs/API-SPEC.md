# 귀가마중 API 명세서

앱과 서버가 서로를 보지 않고도 각자 만들 수 있도록 형식을 못박는다.

참조 구현이 [`Server/homecoming_server.py`](../Server/homecoming_server.py) 에 있다.
파일 하나, 의존성 없음. 실서비스 서버를 만들기 전에 이걸로 앱을 끝까지 시험할 수 있다.

## 범위

| | 내용 | 상태 |
|---|---|---|
| **Phase 1** | 귀가자가 귀가 시작을 누르면 가족이 진행 상황과 도착 예정을 본다 | 이 문서의 기본 |
| **Phase 2** | 안전귀가 — 안심 확인, 이상 상황 판정 | 표시만 해 둠 |

Phase 2 항목에는 **`[P2]`** 를 붙였다. 지금 서버를 만들 때는 건너뛰어도 된다.
앱 코드에는 이미 들어가 있지만 `safetyMode` 가 꺼져 있으면 나타나지 않으며,
`content-state` 의 `checkInDeadline` · `anomaly` 는 둘 다 선택 키라 빼고 보내면 그만이다.

이 문서의 페이로드는 손으로 적은 게 아니라 **실제 Swift 타입에서 뽑아낸 것**이다.
코드를 고쳤으면 다시 뽑아서 갱신한다:

```bash
xcrun simctl launch <udid> com.kona.homecoming2 -homecomingPrintContract
xcrun simctl spawn <udid> log show --last 1m \
  --predicate 'subsystem == "com.kona.homecoming2" AND category == "push"' --style compact
```

## 1. 왜 서버가 필요한가

이 서비스는 **귀가자가 귀가 시작을 누르면 집에 있는 가족이 본다**. 그런데 iOS 기기는
다른 기기에 Live Activity 를 띄울 수 없다. 반드시 서버를 거쳐야 한다.

```
귀가자 기기                서버                     가족 기기 (N대)
  위치·체크인  ──────────>  ETA 계산                    
                            이상 판정                   
                            도착 판정                   
                                    ──── APNs ────>  Live Activity
```

그래서 **가족 기기는 아무것도 계산하지 않는다.** 서버가 밀어 주는 것을 그릴 뿐이다.
이상 판정(멈춰 있음·무응답·연락 두절)이 서버 몫인 이유이기도 하다 —
그 상황들은 정의상 기기가 조용할 때 성립해서, 기기 자신은 판단할 수 없다.

## 2. 지켜야 할 원칙

### content-state 는 모든 수신자에게 **동일하다**

한 번의 귀가에 대해 액티비티가 여러 개 뜬다(본인 1 + 가족 N). 화면은 다르지만
**표시되는 사실은 같아야 한다.** 가족이 보는 도착 예정 시각과 본인이 보는 것이
다르면 그 순간 서비스는 믿을 수 없는 것이 된다.

따라서 서버는 `content-state` 를 **한 번 계산해서 가족 각자에게 그대로 나눠 보낸다**.
수신자마다 다른 것은 `attributes.audience` 하나뿐이다.

| | 귀가자 (`traveler`) | 가족 (`watcher`) |
|---|---|---|
| 헤드라인 | "가족에게 공유 중" | "아빠 집으로 가는 중" |
| 안심 확인 `[P2]` | **버튼** (누를 수 있음) | 남은 시간 표시만 |
| 도착 예정 · 카운트다운 | **동일** | **동일** |
| 진행 바 · 남은 거리 | **동일** | **동일** |
| 이상 상황 | **동일** | **동일** |

화면 분기는 전부 앱 안에 있다. 서버는 `audience` 만 정확히 넣으면 된다.

### 날짜는 ISO8601 문자열

Swift 의 기본 `Date` 인코딩은 **2001-01-01 기준 초**라는 숫자를 쓴다.
서버가 Unix epoch 를 넣으면 타입이 맞아 에러 없이 통과하고 값만 31년 어긋난다.
그래서 `content-state` / `attributes` 안의 모든 날짜는 문자열로 못박았다.

```
"expectedArrival": "2026-08-14T19:24:00Z"
```

소수점 초는 있어도 되고 없어도 된다. 타임존은 `Z` 또는 오프셋 표기 모두 받는다.

> `aps.timestamp` 와 `aps.dismissal-date` 는 예외다. 이건 우리 타입이 아니라
> **Apple 이 정의한 필드**라서 Unix epoch 정수를 그대로 쓴다.

## 3. 앱 → 서버

### 3.0 인증

`GET /health` 와 `POST /device/register` 를 뺀 **모든 요청은 토큰을 들고 와야 한다.**
없거나 틀리면 `401` 이다.

```
Authorization: Bearer <token>
```

토큰은 기기가 처음 켜질 때 한 번 받는다.

```
POST /device/register  { }
                       → { "accountId": "1cfd2fd06d39", "token": "<hex 64자>" }
```

앱은 받은 토큰을 **키체인**에 넣는다(`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`).
UserDefaults 는 안 된다 — `devicectl device copy` 로 뽑아낼 수 있다.

서버는 **sha256 만 저장한다.** 평문은 이 응답에만 실려 나간다. 그래서 잃어버린
토큰을 되찾을 방법이 없고, 그건 의도다 — 되찾아 줄 수 있으면 남도 되찾아 갈 수 있다.

**`401` 은 "다시 등록하라" 는 뜻이다.** 앱은 자격을 버리고 `POST /device/register`
로 새로 받아 그 요청을 한 번 더 보낸다. 이게 없으면 서버 쪽에서 토큰이 사라지는
순간(DB 초기화, 저장 방식 변경, 계정 정리) 앱은 같은 죽은 토큰을 영원히 다시
보내면서 영구히 멈춘다 — 귀가는 시작되지 않고 가족은 아무것도 못 본다.
재등록은 **새 계정**이므로 가족 연결은 다시 맺어야 한다.

> **왜 계정 id 를 헤더로 믿지 않는가.** 예전에는 `X-Account-Id` 를 그대로 믿었다.
> 계정 id 는 짐작하거나 가족 목록(`GET /pair/watchers`)에서 그냥 읽을 수 있는 값이라,
> 남의 id 를 적어 넣으면 그 사람의 귀가를 조작하거나 위치를 들여다볼 수 있었다.
> 지금은 계정을 **토큰으로만** 찾는다. 그래서 요청 본문에 `accountId` 를 적는 자리가
> 아예 없다 — 적을 자리가 있으면 언젠가 그게 믿어진다.
>
> 세션은 소유자만 만질 수 있다. 남의 세션에 위치를 넣거나 끝내려 하면 `403` 이 아니라
> **`404`** 를 준다. `403` 은 "그 세션은 있는데 네 것이 아니다" 를 알려 주는 셈이라,
> 남의 귀가가 지금 진행 중인지 떠보는 데 쓸 수 있다.

**다시 설치해도 같은 계정이다.** iOS 는 앱을 삭제해도 키체인을 지우지 않는다.
실기기에서 지웠다 다시 깔아 보니 같은 계정 id 로 돌아왔다. 가족 연결도 살아 있다.
(이 문서는 한동안 반대로 적혀 있었다.)

**기기를 바꾸면 이어지지 않는다.** 복구 수단은 두지 않았다 — 계정 복구를 하려면
사용자를 식별할 무언가(전화번호, 애플 로그인)가 필요하고, 그건 이 앱이 아직 하지
않는 일이다.

### 3.1 토큰 등록

앱이 받은 APNs 토큰을 올린다. 세 종류 모두 언제든 재발급되므로, 올 때마다 덮어쓴다.
어느 계정의 토큰인지는 `Authorization` 헤더가 말한다.

```
POST /push/device        { "deviceToken": "<hex>" }
POST /push/start-token   { "token": "<hex>" }
POST /push/activity      { "activityId": "...", "token": "<hex>",
                           "travelerName": "아빠" }
POST /push/activity/end  { "activityId": "..." }
```

| 토큰 | 쓰임 |
|---|---|
| `deviceToken` | 일반 푸시. **Live Activity 에는 쓰지 않는다.** 실시간 활동이 꺼져 있을 때의 폴백 채널로만 의미가 있어, Phase 1 에서는 선택 사항 |
| `start-token` | **push-to-start.** 앱이 떠 있지 않아도 액티비티를 시작시킨다. 가족 기기에 알림을 띄우는 건 전적으로 이것에 달려 있다 |
| `activity` | 이미 뜬 액티비티에 새 상태를 밀어 넣는다. 액티비티마다 다르다 |

계정 id 는 기기마다 하나다. 로그인이 붙으면 사용자 식별자로 대체한다.

> **토큰은 앱을 다시 설치할 때마다 바뀐다.** 실기기 테스트에서 확인했다.
> 그리고 스트림은 값이 **바뀔 때만** 흐르므로, 앱을 다시 켰다고 다시 주지 않는다.
> 서버는 같은 `accountId` 로 새 토큰이 오면 옛 것을 버리고 덮어써야 하고,
> 앱은 마지막 값을 들고 있다가 등록에 실패하면 재시도해야 한다.

### 3.2 페어링 *(앱 · 참조 서버 모두 구현)*

가족 기기가 어떻게 연결되는지. 최소한 이만큼은 있어야 한다.

```
POST /pair/invite     { "travelerName": "아빠" }
                      → { "code": "8FQ2K", "expiresAt": "2026-08-13T12:00:00Z" }
POST /pair/accept     { "code": "8FQ2K", "name": "엄마" }
                      → { "travelerName": "아빠", "travelerAccountId": "..." }
GET  /pair/watchers   → [{ "accountId": "...", "name": "엄마" }]     내 귀가를 보는 가족
GET  /pair/watching   → [{ "accountId": "...", "name": "아빠" }]     내가 지켜보는 사람
DELETE /pair/link/{accountId}                                   양쪽 다 자기 쪽에서 끊을 수 있다
```

**귀가자가 승인 주체다.** 보호자가 일방적으로 붙일 수 있으면 감시 도구가 된다.

해제는 **양쪽 다** 가능해야 한다. 귀가자만 끊을 수 있으면 가족이 원치 않는 연결에 묶이고,
가족만 끊을 수 있으면 귀가자가 통제를 잃는다.

초대 코드는 헷갈리는 글자(`O`/`0`, `I`/`1`)를 뺀 5자리, 30분 유효.
전화로 불러 줄 수 있어야 하기 때문이다.

| 상태 | 응답 |
|---|---|
| 없는 코드 | `404` |
| 만료된 코드 | `410` |
| 자기 자신을 연결 | `400` |

### 3.3 세션 *(앱 · 참조 서버 모두 구현)*

**세션**은 귀가 시작을 누른 순간부터 도착(또는 중지)까지의 한 건이다.
서버가 시작·위치·종료·가족 각자에게 보내는 일을 하나로 묶는 단위이고, 그래서 ID 가 필요하다.

```
POST /session/start
{
  "home": { "lat": 37.53, "lon": 126.98, "arrivalRadius": 150, "name": "집" },
  "travelerName": "아빠",
  "safetyMode": false,
  "routeId": "3f2a1c9d8e00",   // 저장된 경로로 도는 귀가면
  "plannedMinutes": 60,         // 경로 없이 도는 귀가에서 귀가자가 적은 소요시간
  "lat": 37.53, "lon": 126.98,  // 출발 좌표. 첫 카드부터 지도를 그리게 한다
  "checkInInterval": 900        // [P2] safetyMode 가 true 일 때만
}
→ { "sessionId": "..." }

POST /session/{sessionId}/location
{ "lat": 37.55, "lon": 126.98, "accuracy": 12, "at": "2026-08-14T18:40:00Z" }

POST /session/{sessionId}/checkin    [P2]
POST /session/{sessionId}/end        { "reason": "arrived" | "stopped" }
```

**`routeId` 와 `plannedMinutes` 는 둘 중 하나다.** 둘 다 도착예정의 근거이고, 둘 다
추정이 아니라 **아는 값**이다 — 앞은 경로에 적힌 실측 소요시간, 뒤는 귀가자가 적은
시간. 경로가 있으면 서버는 `plannedMinutes` 를 보지 않으므로 앱은 그때 키를 빼고
보낸다. 둘 다 없으면 서버는 20분 자리표시자로 시작해 첫 위치 보고에서 관측 속도로
덮어쓴다 — 그 값이 가장 약하다.

**출발 좌표를 함께 보낸다.** `content_state` 는 좌표가 있을 때만 그것을 싣고, 그 값은
위치 보고에서만 채워졌다. 그래서 세션 시작 푸시에는 좌표가 없어 **가족 카드가 처음 뜰
때 지도가 없었다** — 실제로는 1초 뒤 첫 보고가 메우지만, 그 사이를 보면 고장으로 읽힌다
(2026-08-20 실기기에서 그렇게 짚었다). 없으면 예전대로 돈다.

`end` 의 `reason` 이 중요하다. **가족 화면에서 "도착"과 "공유 중지"는 달라야 한다.**
조용해진 이유를 모르면 안전귀가라고 할 수 없다.

**위치 보고 주기** — 앱이 알아서 조인다. 15초 또는 100m 마다, 집 1km 안에서는 8초 / 40m 마다.
픽스마다 올리면 서버도 배터리도 못 버틴다.

**실패한 보고는 다시 보내지 않는다.** 다음 위치가 곧 그것을 대신하므로 쌓아 둘 이유가 없다.
다만 `session/start` 가 실패하면 서버는 이 귀가를 아예 모르고, 가족은 아무것도 못 본다.
그래서 시작 실패만 화면에 표시한다.

**세션 ID 는 앱이 저장한다.** 귀가 중에 앱이 메모리에서 내려가는 건 예외가 아니라 기본값이라,
다시 켜졌을 때 같은 세션으로 이어 보고해야 한다. 잃어버리면 가족 화면이 마지막 값에서 멈춘다.

**서버가 `404` 를 주면 그 ID 를 버려야 한다.** 서버가 세션을 이미 끝냈을 수 있다
(도착 처리, 24시간 뒤 정리, 다른 기기에서 중지). 그대로 두면 앱은 죽은 세션으로
위치를 계속 보내고 가족은 아무것도 못 본다. `404` 는 다시 보내도 영영 안 되는
오류이므로 다른 실패와 다르게 다뤄, ID 를 버리고 새 세션을 연다.

### 3.4 경로 *(앱 · 참조 서버 모두 구현)*

**도착예정은 계산할 값이 아니라 아는 값이다.** 매일 같은 버스-지하철-버스를 타면
대중교통 앱이 "1시간 24분" 이라고 알려 준다. 그걸 저장해 두면 GPS 로 남은 시간을
추정할 필요가 없다.

```
POST /route
{
  "name": "회사-집",
  "totalSeconds": 5040,
  "home": { "lat": 37.678850, "lon": 127.81591, "name": "집", "radius": 120 },
  "legs": [
    { "mode": "walk", "startsAt": 0, "seconds": 300,
      "toName": "출발역.은행앞",
      "points": [[37.528676, 127.918861], ...] },
    { "mode": "wait", "startsAt": 300, "seconds": 180, "toName": "163번 대기",
      "points": [[37.529, 126.917]] },
    ...
  ]
}
→ { "routeId": "3f2a1c9d8e00", "totalSeconds": 5040 }

GET /route
→ [{ "routeId": "...", "name": "회사-집",
     "totalSeconds": 5040, "homeName": "집" }]
```

| 필드 | 뜻 |
|---|---|
| `mode` | `walk` · `bus` · `subway` · `car` · `wait` |
| `startsAt` | 출발부터 이 구간이 시작되기까지의 초 |
| `seconds` | 이 구간에 걸리는 초. **대중교통 앱의 실측을 그대로 넣는다** |
| `toName` | 도착 지점 이름. 가족 카드의 "풍산역까지 12분" 이 여기서 나온다 |
| `points` | `[[위도, 경도], ...]`. 서버가 "지금 이 구간" 을 판정하는 근거 |

**같은 이름으로 다시 올리면 고치는 것이다.** `(계정, 이름)` 이 유일하고, `routeId` 는
유지된다 — 세션과 앱이 그 id 를 들고 있다. 새로 만들면 고르기 화면에 구분할 수 없는
줄이 쌓인다(실제로 여덟 개까지 쌓였다).

**좌표 없는 구간만 있으면 `400` 이다.** 구간을 판정할 수 없으면 경로가 있어도 쓸 데가
없다. `wait` 는 예외 — 위치는 그대로고 시간만 흐른다.

거절 사유: `legs` 없음 · `totalSeconds` ≤ 0 · `home` 좌표 없음 · 이동 구간에 `points` 없음.

> **애플은 대중교통 좌표열을 주지 않는다.** `MKDirections` 의 `.transit` 은 소요시간만
> 주고 폴리라인을 주지 않는다. 그래서 좌표열은 맥에서 `Tools/route-make.py` 로 구워
> 서버에 올린다 — 버스는 자동차 경로로 대신하고, 지하철은 역 사이 직선으로 잇는다.
> 구간이 km 단위라 이 정도 근사로도 "지금 어느 구간인가" 는 맞힌다.

**경로가 붙은 세션의 도착예정** — `now + (totalSeconds + 지연 - 경과)`.
위치가 하는 일은 두 가지로 줄어든다: 지금 어느 구간인가, 얼마나 밀렸는가.
둘 다 남은 시간을 예측하는 것보다 훨씬 쉽고, 위치가 부정확한 지하철 구간에서도
도착예정이 흔들리지 않는다.

경로 없이 시작한 세션은 **관측 속도**로 떨어진다 — 최근 위치들이 집에 가까워지는
속도로 남은 거리를 나눈다. 이게 왜 열등한지는 실측으로 드러났다. 지하철 구간에서
위치가 튀면 속도가 0 에 가까워지고, 도착예정이 **18.8시간** 으로 뛰었다.
그래서 속도에 하한·상한(1 ~ 30 m/s)을 두고 그래도 남는 오차를 여정 3배로 잘라 낸다.
같은 경로가 경로 모드에서는 84분으로 안정된다.

지연은 "이 구간에 있어야 할 시각" 과 실제 시각의 차이다. 위치마다 튀지 않도록
지수 평활(`DELAY_SMOOTHING = 0.25`)로 눌러 두고, 60초를 넘을 때만 카드에 보여 준다.

## 4. 서버 → APNs

### 4.1 헤더

```
apns-push-type: liveactivity
apns-topic: com.kona.homecoming2.push-type.liveactivity
apns-priority: 10        (이상 상황·도착)  /  5 (일반 이동 갱신)
apns-expiration: <unix>
```

`start` 이벤트는 **push-to-start 토큰**으로, `update`/`end` 는 **액티비티 갱신 토큰**으로 보낸다.

> **`apns-topic` 은 번들 ID 에서 파생된다.** 번들 ID 를 바꾸면 이 헤더도 함께 바뀌고,
> 개발자 계정의 App ID · 프로비저닝 · 엔타이틀먼트도 새로 만들어야 한다.
> 서버 작업을 시작하기 전에 번들 ID 를 확정하는 편이 낫다.
> 지금은 `com.kona.homecoming2` (위젯은 `.widget`) 으로 잡혀 있다.

### 4.2 start

액티비티를 처음 띄운다. `attributes` 와 `attributes-type` 이 이때만 필요하다.

```json
{
  "aps" : {
    "alert" : {
      "body" : "엄마가 집으로 출발했어요",
      "title" : "귀가 시작"
    },
    "attributes" : {
      "audience" : "watcher",
      "departedAt" : "2026-08-14T16:24:00Z",
      "destinationName" : "집",
      "travelerName" : "엄마"
    },
    "attributes-type" : "HomecomingAttributes",
    "content-state" : {
      "checkInDeadline" : "2026-08-14T16:54:00Z",
      "detail" : "2호선 · 3정거장 남음",
      "estimateSource" : "route",
      "expectedArrival" : "2026-08-14T19:24:00Z",
      "measuredAt" : "2026-08-14T19:10:00Z",
      "remainingMeters" : 4200,
      "stage" : "moving",
      "totalMeters" : 11000,
      "transport" : "subway",
      "travelledMeters" : 6800
    },
    "event" : "start",
    "timestamp" : 1786724640
  }
}
```

가족이 3명이면 이 요청을 3번 보낸다. `content-state` 는 **완전히 같고**,
`attributes.audience` 만 각자에 맞춘다(가족은 `watcher`, 본인은 `traveler`).

### 4.3 update

```json
{
  "aps" : {
    "alert" : {
      "body" : "엄마 · 예정보다 늦어요",
      "title" : "지연"
    },
    "content-state" : {
      "anomaly" : "delayed",
      "checkInDeadline" : "2026-08-14T16:54:00Z",
      "delaySeconds" : 480,
      "detail" : "아파트 정문 앞",
      "estimateSource" : "offRoute",
      "expectedArrival" : "2026-08-14T19:40:00Z",
      "measuredAt" : "2026-08-14T19:34:00Z",
      "remainingMeters" : 240,
      "stage" : "nearby",
      "totalMeters" : 11000,
      "transport" : "walk",
      "travelledMeters" : 8600
    },
    "event" : "update",
    "timestamp" : 1786726500
  }
}
```

이 표본은 **이탈 중**이다(`estimateSource: "offRoute"`). 그래서 `remainingMeters`
가 집까지 직선거리(240m)이고, `travelledMeters` 는 경로 위에서 8,600m 에 서 있다.
되짚으면(`11000 - 240`) 10,760m 가 되어 노선도의 점이 앞으로 튄다 — 두 값을
섞으면 안 되는 이유가 이 한 쌍이다.

`alert` 는 **넣을 때만 화면이 깨어난다.** 이동 중 갱신에는 넣지 않는다.
매번 울리면 사람들이 알림을 꺼 버리고, 그러면 정말 울려야 할 때 아무도 못 본다.

울릴 것: 도착, `stage` 가 `nearby` 로 처음 올라설 때.
`[P2]` `anomaly` 가 `unresponsive` · `offRoute` · `disconnected` 로 새로 바뀔 때.

울리지 말 것: 이동 중 위치 갱신. `[P2]` `delayed` · `stalled`.

### 4.4 end

```json
{
  "aps" : {
    "content-state" : {
      "estimateSource" : "route",
      "expectedArrival" : "2026-08-14T19:45:00Z",
      "measuredAt" : "2026-08-14T19:45:00Z",
      "remainingMeters" : 0,
      "stage" : "arrived",
      "totalMeters" : 11000,
      "transport" : "walk",
      "travelledMeters" : 11000
    },
    "dismissal-date" : 1786736760,
    "event" : "end",
    "timestamp" : 1786736700
  }
}
```

> **다이나믹 아일랜드는 `end` 를 받는 즉시 알림을 치운다.**
> `dismissal-date` 는 잠금화면에만 적용된다. 그래서 도착했을 때는
> 먼저 `stage: "arrived"` 로 **update** 를 보내 20초쯤 보여 준 뒤 `end` 를 보낸다.
> 기다리던 가족이 실제로 보는 건 그 몇 초다.
>
> `reason: "stopped"`(공유 중지)일 때는 **`endReason: "stopped"`** 을 넣고
> `stage` 는 그대로 둔다. 도착하지 않았는데 도착으로 보이면 안 된다.
>
> 앱은 이 값을 보고 화면을 완전히 다르게 그린다 — 회색, 눈 가림 아이콘,
> "공유를 껐어요", 카운트다운 자리에 "중지". 도착 예정 시각은 감춘다.
> **조용해진 이유를 가족이 알 수 있어야 한다는 요구가 여기서 지켜진다.**

## 5. content-state 스키마

| 키 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `stage` | enum | ✓ | 진행 단계. **뒤로 가지 않는다** |
| `transport` | enum | ✓ | 이동 수단 |
| `expectedArrival` | ISO8601 | ✓ | 도착 예정 **시각**. 남은 분이 아니다 |
| `remainingMeters` | Int | ✓ | 남은 경로 거리 |
| `totalMeters` | Int | ✓ | 출발 시점 전체 거리. 진행률 계산용 |
| `travelledMeters` | Int | | 경로 위에서 지나온 거리. **노선도의 점과 지도의 색 분리가 함께 쓴다** |
| `detail` | String | | "2호선 · 3정거장 남음" 같은 한 줄 |
| `delaySeconds` | Int | | 저장된 경로 기준으로 밀린 시간. **1분 미만은 보내지 않는다** |
| `measuredAt` | ISO8601 | | 이 값들이 **언제의 위치로** 만들어졌는지 |
| `estimateSource` | String | | 어떻게 낸 값인지. `route` / `offRoute` / `distance` (아래) |
| `lat` · `lon` | Double | | 귀가자의 지금 자리. **다섯이 한 덩어리다**(아래) |
| `homeLat` · `homeLon` | Double | | 집 |
| `homeRadius` | Int | | 도착 반경(m). 지도가 집 주위에 원으로 그린다 |
| `checkInDeadline` | ISO8601 | | `[P2]` 안심 확인 마감. **없으면 안전귀가 모드가 아니다** |
| `anomaly` | enum | | `[P2]` 이상 상황. 없으면 키를 빼거나 `null` |
| `endReason` | enum | | 왜 끝났는지. `end` 이벤트에서만 채운다 |

### 좌표 다섯은 왜 한 덩어리인가

**`lat`/`lon` 이 없으면 나머지도 안 보낸다.** 서버가 같은 `if` 안에서 다섯을 함께
싣는다 — 첫 위치 보고 전에는 `last_lat` 이 비어 있고, 그때는 키를 아예 넣지 않는다.
앱은 좌표가 없으면 지도를 그리지 않는다(`HomecomingJourneyMap` 은 `travelerCoordinate`
가 nil 이면 자리를 만들지 않는다). **빈 회색 사각형은 "위치를 모른다" 보다
"고장났다" 로 읽히기 때문이다.**

그래서 `lat` 은 있는데 `homeLat` 이 없는 상태는 서버가 만들지 않는다. 지도가 담을
것을 정할 때(`region()`) 이걸 전제한다.

**집은 세션 안에서 바뀌지 않는데도 갱신값에 싣는다.** 고정값(`attributes`)에 넣으면
push-to-start 경로까지 건드려야 하고, 좌표 두 개가 는다고 4KB 한도에 가까워지지도
않는다.

**도착 반경을 함께 보내는 이유는 화면이 판정을 설명해야 하기 때문이다.** 서버는 이
반경 안에서 단계를 `nearby` 로 올린다. 지금까지 "곧 도착" 은 지리적 설명 없이 나타났다
— 판정에 쓰는 값과 그리는 값이 같아야 화면이 거짓말을 하지 않는다.

### `measuredAt` 은 왜 필요한가

**낡음의 기준은 배달 시각이 아니라 측정 시각이다.**

2026-08-18 실주행에서 갱신이 APNs 안에서 최대 27분 붙잡혀 있다가 내려왔다
(`apns-priority: 5` 였다). 폰은 방금 받았으므로 화면의 "N분 전 확인" 이 뜨지 않았고,
27분 전 자리를 아무 표시 없이 지금 자리처럼 보여 줬다. 받은 시각으로는 이 상태를
가려낼 수 없다.

`aps.timestamp` 로는 안 된다 — ActivityKit 이 앱에 넘겨 주지 않는다. 그래서
`content-state` 안에 싣는다.

### `travelledMeters` 는 왜 따로 보내는가

**`totalMeters - remainingMeters` 로 되짚으면 안 되기 때문이다.**

`remainingMeters` 는 **뜻이 바뀌는 값**이다. 경로 위에서는 경로를 따라 잰 거리지만,
벗어나면 서버가 집까지 직선거리로 바꾼다(`estimateSource: "offRoute"`). 직선은
경로보다 짧으니 되짚은 값이 커진다 — 화면은 "많이 왔다" 로 읽는다. 2026-08-20
실측에서 60% 지점에서 옆으로 1.5km 빠졌는데 노선도의 점이 85% 로 **전진했다.**

`travelledMeters` 는 서버의 `route_progress` 에서 나오고 성질이 다르다.

- 뒤로 가지 않는다 (GPS 가 흔들려도 점이 되돌아가지 않는다)
- 이탈하면 **갱신을 멈출 뿐** 뜻이 바뀌지 않는다
- 경로 위에서만 정의된다 (경로 없이 시작한 귀가면 키가 없다)
- 도착하면 경로 전체 길이다 (`route_progress` 는 끝까지 가지 않는다)

**자는 정류장 거리와 같다**(`route_length()`, 좌표열을 따라 잰다). `totalMeters` 와
견주면 안 된다 — 그쪽은 액티비티를 시작한 앱이 넣은 값이라 MapKit 자동차 거리에서
올 수 있다. 노선도의 분모는 `attributes.routeShape` 의 정류장 거리 합이다.

카드(노선도)와 지도(지나온/남은 색 분리)가 **이 한 값을 함께 쓴다.** 예전에는 각자
계산해서 정상 이동에서는 평균 36m 로 맞았지만 GPS 역행에서 7,404m, 이탈에서
4,349m 갈라졌다. `python3 Tools/verify-progress-sync.py` 가 그 차이를 다시 잰다.

### `estimateSource` 는 왜 문자열인가

앱은 자기가 저장된 경로로 시작한 것만 알고, **서버가 도중에 경로를 벗어나 직선거리
추정으로 되돌아간 것은 모른다.** 그래서 서버가 밝힌다.

**`offRoute` 는 "전부 직선으로 짐작한다" 는 뜻이 아니다.** 남은거리만 직선이고
**도착예정은 경로의 시간 예산에서 그대로 나온다** — `총소요시간 + 지연 − 경과시간`
이라 위치를 아예 안 쓰기 때문이다. 위치가 벗어났다고 시간 계산까지 버릴 이유가 없다.

2026-08-25 실주행이 그 근거다. 18:09 에 1,105m 로 이탈해 도착까지 39분을 직선거리
추정으로 돌았는데, 저장된 경로의 예정(18:54)은 실제 도착(18:48:39)과 **6분** 차이였고
직선 폴백의 예정(~18:30)은 **18분** 틀렸다. 게다가 예정이 앞당겨지면서 가족이 도착한
줄로 읽었다.

`enum` 이 아니라 `String` 인 이유는 아래 "여기 없는 문자열" 규칙 때문이다 — 나중에
값을 하나 더 넣어도 구버전 앱의 디코딩이 깨지면 안 된다. 앱은 아는 값만 해석하고
모르는 값은 무시한다.

### enum 값

```json
{
  "stage"     : ["leaving", "moving", "nearby", "arrived"],
  "transport" : ["subway", "bus", "car", "walk"],
  "anomaly"   : ["delayed", "stalled", "offRoute", "unresponsive", "disconnected"],
  "audience"  : ["traveler", "watcher"],
  "endReason" : ["arrived", "stopped"]
}
```

여기 없는 문자열을 보내면 **디코딩이 실패해 푸시가 통째로 버려진다.** 조용히.

`estimateSource` 는 이 목록에 없다. 일부러 `String` 으로 뒀다 — 위 절을 보라.

**`content-state` 에 키를 더할 때는 `Shared/HomecomingAttributes.swift` 의
`ContentState.CodingKeys` 와 `init(from:)` · `encode(to:)` 도 같이 고쳐야 한다.**
그 셋은 손으로 쓴 것이라 목록에 없는 키는 조용히 nil 로 남는다. 컴파일도 되고 푸시도
성공하고 에러도 없이 값만 사라진다 — `delaySeconds` 가 그렇게 빠져 있었고, 서버가
2026-08-18 실주행 내내 지연을 실어 보냈는데 배지가 한 번도 뜨지 않았다.

### 지켜야 할 불변식

- `stage` 는 뒤로 가지 않는다. GPS 가 튀어 "곧 도착"이 "이동 중"으로 되돌아가면
  기다리는 가족이 혼란스럽다. 서버가 단조성을 보장한다.
- `anomaly` 는 `stage` 와 **다른 축**이다. 늦어지다 따라잡을 수도 있고 도착 직전에
  멈출 수도 있다. 떴다 사라지는 값이므로 `stage` 에 섞지 않는다.
- 여러 이상이 동시에 성립하면 심각한 하나만 보낸다:
  `disconnected` > `unresponsive` > `offRoute` > `stalled` > `delayed`
- `totalMeters >= remainingMeters`.
- `travelledMeters` 는 줄지 않는다. 도착하면 경로 전체 길이다.
  **`totalMeters - remainingMeters` 와 같다고 보면 안 된다** — 이탈에서 갈라진다.

## 6. 이상 상황 판정 기준 `[P2]`

> **Phase 2.** 아래는 안전귀가를 붙일 때 서버가 맡아야 할 몫이다.
> Phase 1 에서는 `anomaly` 를 보내지 않는다.

앱에도 같은 로직이 있지만(`SafetyWatch`) 그건 앱이 깨어 있는 동안의 보조 장치다.
**판정의 주체는 서버다.**

| 값 | 기준 | 판정 주체 |
|---|---|---|
| `delayed` | 도착 예정 + 10분 초과 | 서버 |
| `stalled` | 80m 안에서 8분 이상, 집 400m 밖 | 서버 |
| `offRoute` | 예상 경로 폴리라인에서 이탈 | 서버 (앱은 못 함) |
| `unresponsive` | 안심 확인 마감 초과 | 서버 |
| `disconnected` | 위치가 N분 이상 안 올라옴 | 서버 (앱은 못 함) |

> **지하 구간 주의.** 지하철에서는 GPS 가 통째로 끊긴다.
> 마지막 위치가 역 근처였다면 `disconnected` 판정을 유예해야 한다.
> 그러지 않으면 매일 귀가할 때마다 가족에게 경보가 울린다.

## 7. 오류 처리

| 상황 | 처리 |
|---|---|
| APNs 410 Gone | 토큰 폐기. 다음 세션에서 재발급을 기다린다 |
| APNs 400 `BadDeviceToken` | 같음 |

## 8. 검증된 것

### 실기기 (iPhone 14 Pro Max, iOS 18.7.3) — APNs 실제 전달

`Tools/apns-push.py` 로 이 문서의 페이로드를 그대로 쏴서 확인했다.

- **`start` — 앱이 실행 중이 아닌데 액티비티가 생성됨.** 가족 기기에 띄우는 그 경로다
- `attributes` 디코딩 — `audience: "watcher"`, `travelerName: "엄마"` 반영
- **ISO8601 날짜가 ActivityKit 푸시 디코더에서 정상 처리됨.**
  숫자가 아니라 문자열로 못박은 선택이 실제로 통한다는 확인이다
- `update` — `stage` · `remainingMeters` · `detail` 전부 보낸 값 그대로 반영
- 값 정확성 — `remainingMeters: 8888` 을 보내면 기기에 정확히 8888 이 들어간다

### 시뮬레이터 — 목 서버 (`Tools/mock-server.py`)

- `POST /eta` 왕복 — 요청 형식, ISO8601 응답 파싱, `mode` → 이동 수단 매핑, `detail` 반영
- 토큰 3종 등록
- 폴백 — 서버 500, 응답 지연(타임아웃) 모두 MapKit 으로 넘어감
- **세션 한 건 전체** — `session/start` → `sessionId` 수령 → 위치 보고 → `end (arrived)`
- **앱을 강제 종료했다 켜도 같은 세션으로 보고가 이어짐**
- **페어링 왕복** — 초대 코드 발급 → 다른 계정이 입력 → 양쪽 목록 반영 → 해제
- 없는 코드는 `404` 로 걸러지고 화면에 안내가 뜬다

### 참조 서버 (`Server/homecoming_server.py`)

- 페어링 → 세션 시작 → 가족에게 시작 알림 → 위치 갱신 → 도착 판정 → 종료 한 바퀴
- 단계 단조 증가, 도착 반경 판정, 관측 속도 기반 ETA 보정
- 앱과의 연결 — 앱이 보낸 `GET /pair/*` 가 올바른 `Authorization: Bearer` 로 도착
- 인증 — 토큰 없이·틀린 토큰으로·옛 `X-Account-Id` 헤더로 모두 `401`,
  남의 세션에 위치를 넣거나 끝내려 하면 `404`

### 확인 과정에서 잡은 결함

**앱이 재시작되면 서버 세션이 끊겼다.** 위치 추적은 되살아나는데 세션 ID 를 잃어버려서,
본인 화면만 멀쩡하고 가족 화면은 마지막 값에서 그대로 멈췄다.
세션 ID 를 저장했다가 복구하도록 고쳤다.

가족 기기의 앱이 서버가 밀어 준 액티비티를 **자기 계산으로 덮어쓰고 있었다.**
`remainingMeters: 9800` 을 보냈는데 기기에서 26,354 로 바뀌어 있었다.
앱이 액티비티를 다시 붙잡을 때(`reattach`) 역할을 가리지 않아, 가족용 액티비티까지
자기 것으로 여기고 위치 갱신을 밀어 넣은 탓이다.

**앱은 `audience == .traveler` 인 액티비티만 건드린다.** 가족 기기는 그리기만 한다.
