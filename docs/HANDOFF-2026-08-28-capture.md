같은 날 앞 회차([`HANDOFF-2026-08-28.md`](HANDOFF-2026-08-28.md))에 이어진다.
그 문서의 **`다음 작업 1번` 을 끝냈다.**

배포 정보와 이 환경의 함정은 [`HANDOFF-2026-08-20.md`](HANDOFF-2026-08-20.md) 에 있다.

이 회차에 **길찾기 앱 캡처를 읽어 편집기를 채우게** 했다. 경로 하나를 만드는 데
입력이 25번이었다.

그 뒤 **화면을 손봤다** — 지도와 카드를 가르고, 지도가 사람 손을 밀어내던 것을
고치고, 도착예정이 잠깐 튀던 원인을 찾았다.

시험 200개 → **246개**. 서버 배포 완료. 앱은 실기기에 설치됨.

그리고 **원래 있던 구멍 하나를 찾아 고쳤다** — 버스 구간 선이 노선을 안 훑고
자동차 경로로 그려지고 있었다. 외부 API 가 32초로 느려졌는데 우리 타임아웃이
15초였다.

## 다음 작업, 순서대로

**1. 구간이 바뀌는 순간의 화면 (가장 앞)**

앞 회차부터 남아 있다. 2026-08-28 실귀가는 끝까지 깨끗했지만, 구간이 바뀌는 그
순간의 **문구·아이콘·노선도의 점**을 따로 보지는 않았다. 그 넷이 같은 순간에 같은
값에서 나와야 한다 — 하나만 늦으면 한 화면 안에서 어긋난다.

볼 자리는 `신촌로터리에서 내려 서강대역까지 걷는 구간` 이다(버스 → 도보).

**정류장에서 기다리는 동안 칩이 999를 계속 가리켰다**(사용자 확인, 2026-08-28).
로그도 같다 — 서 있던 5분 내내 `버스 999 도착 새로고침` 이었다.

**다만 이것으로 `next_bus_leg` 의 좌표 규칙이 증명된 것은 아니다.** 그 규칙은
*"시간표가 넘어갔다고 탄 것은 아니다"* 를 다루는데, 그날은 시간표를 넘기지 않았다.

```
999 구간 시작    startsAt 3840초 = 64분
서 있던 시간      09:28:37 ~ 09:33:49
도착             09:47:33 (계획 77분이면 출발 ≈ 08:30:33)
→ 그때 경과가 58~63분. 승차 예정 64분에 아직 안 닿았다
```

999가 **아직 안 지난 구간**이라 좌표 규칙 없이도 「다음」으로 나온다. 그 규칙이
실제로 도는지는 **버스가 늦어 승차 시각을 넘긴 채 서 있을 때**라야 드러난다.
아직 그 상황을 못 만났다.

**2. 잠금화면에서 버스 새로고침**

설계만 해 뒀다(아래). 자격 코드를 `Shared/` 로 옮기는 일이라 실귀가를 한 번 지난
지금이 붙일 때다.

**3. 서울에 `종점 방면` (선택, 값이 낮다)**
앞 회차 문서 그대로. `다음 정류장` 으로 이미 방향이 갈린다.

### 재고 나서 설계가 셋 바뀌었다

**캡처 없이 설계하지 않았다.** 실기기 캡처 세 장을 받아 다섯 가지를 재고 시작했고,
그중 셋이 앞 회차에 적어 둔 계획을 바꿨다.

**(1) 기둥번호가 캡처에 찍혀 있다 — `seq` 차 규칙 숙제가 사라졌다.**

앞 회차 문서에는 *"캡처엔 좌표가 없어 하차 후보가 둘로 남을 수 있다. 그때 `seq`
차 규칙을 넣을지 정한다"* 로 남아 있었다. 정류장 이름 밑에 `19132`·`14205`·
`20753`·`20796` 이 **신뢰도 1.00 으로** 찍혀 있다.

이름만으로는 안 정해진다(실측).

```
신촌로터리       서울 표에 4건    14168 · 14169 · 14204 · 14205
풍산역          GBIS 에 9건, 그중 이름이 똑같은 기둥 넷
위시티1.3단지    GBIS 에 2건     20795 · 20796
```

**노선으로 좁혀도 안 정해진다.** 999 로 좁혀 재 봤다 — 999 는 265개 기둥에 선다.

```
풍산역 + 999        9건 → 2건   20753(다음: 애니골입구) · 58271(다음: 밤가시7.8단지)
위시티1.3단지 + 999  2건 → 2건   20795(다음: 고양국제고) · 20796(다음: 위시티3.4단지)
```

길 양쪽이 끝까지 남는다. `narrow_by_route` 의 주석이 이미 적어 둔 한계다.
**캡처의 번호가 그 둘 중 하나를 짚는다.** 같은 주석의 다른 한 줄은 낡았다 —
*"그 번호는 기둥에 가서 봐야 아는 값이다."* 캡처에서는 안 가도 읽힌다.

**(2) 출발지 주소는 좌표로 못 바꾼다.**

```
CLGeocoder(도로명 주소)   → kCLErrorDomain error 8                    실패
MKLocalSearch(같은 주소)  → 국회의사당 · KB국민은행 · Hyundai Card Building
```

`PlaceSearch` 의 주석이 기록한 실패가 **도로명 주소에서도** 그대로 난다. 그리고
검색은 근처 가게를 준다 — 2026-08-20 의 `GS25까지 9분` 함정이다. **그래서 안
채운다.** 읽은 주소를 출발 칸 밑에 글자로만 적어 사람이 맞는지 본다.

**(3) 파서를 앱이 아니라 서버에 뒀다 — 앞서 내가 한 판단이 틀렸다.**

처음에 "글자도 밖으로 안 보낸다" 며 앱에 두려 했는데 근거가 약했다. 재 보니
**집 이름과 좌표는 이미 서버에 있다** — `routes` 테이블의 `home_name`·`home_lat`·
`home_lon` 이고 도착 알림 문구가 그걸 읽는다(`{집이름}에 도착했어요`). 경로를
저장하면 구간 이름·노선번호·좌표열이 전부 올라간다.

캡처 줄에서 **새로 나가는 것은 출발지 주소 문자열과 화면 잡동사니뿐**이고, 주소는
앱이 뺀다. **이미지는 어느 쪽이든 폰을 안 떠난다** — 앞 회차에서 정한 것이 그것이고
그대로다.

서버에 두어 얻은 것 셋.

1. **깨질 코드다.** 길찾기 앱이 화면을 바꾸면 문법이 깨진다. 서버면 배포 한 번,
   앱이면 재빌드·재설치다.
2. **시험이 거기 있다.** 34개를 파이썬에 붙였다. 앱에 두면 파서를 만질 때마다
   실기기를 로컬 서버에 붙이게 되는데 — **그때 앱 자격이 끊긴다**(앞 회차 함정).
3. **왕복이 1회다.** 서버가 이미 정류장 조회를 갖고 있다.

같다 — 확인 화면을 따로 안 만든 이유가 그것이다.

### OCR — 애플 Vision 이다. 의존성이 없다

`VNRecognizeTextRequest` 한 개. 서드파티도 API 키도 요금도 없고 폰에서 끝난다.

정한 값 셋 중 **`usesLanguageCorrection = false` 가 가장 중요하다.** 켜면 사전을
보고 말이 되게 고치려 드는데, 이 기능이 읽는 것의 핵심이 `19132`·`6713` 같은 **뜻
없는 번호**다. 한 자가 바뀌면 3km 떨어진 정류장이 나온다.

`recognitionLanguages = ["ko-KR", "en-US"]` — 한국어는 iOS 16부터다. 목록을 실제로
찍어 확인했다. `recognitionLevel = .accurate` — 세 장 한 번 읽는 일이라 아깝지 않다.

직접 쓴 코드는 사실 한 줄이다.

```swift
let sorted = found.sorted { $0.boundingBox.maxY > $1.boundingBox.maxY }
```

**Vision 은 결과를 읽는 순서로 주지 않는다.** 그런데 문법이 순서에 기댄다
(`승차 줄 다음 줄이 기둥번호`). 실제 캡처에서 자료 순서와 화면 순서가 달랐다.

iOS 18 부터 Swift 네이티브 API(`RecognizeTextRequest`, async/await)가 따로 있다.
최소 버전이 17.2(push-to-start)라 못 쓴다 — 나중에 올리면 `withCheckedContinuation`
껍데기를 벗길 수 있다.

### 문법 — 실제 OCR 출력에서만 뽑았다

```
<이름> 승차                국회의사당역.KB국민은행 승차
<노선>선 <역> 승차          경의중앙선 서강대역 승차
<이름> 하차                신촌로터리 하차
<5자리 숫자>               19132 · 14205 · 20753 · 20796   ← 앞 정류장의 기둥
<번호>>                   163>  ·  999>                    ← 승차 뒤 첫 노선
N개 정류장 이동 <구분> M분   4개 정류장 이동 · 9분
N개 역 이동 <구분> M분       12개 역 이동 · 31분
도보 <거리>m <구분> M분      도보 328m. 7분
HH:MM - HH:MM             14:35 - 15:52                   ← 총 시간
<H>시간 <M>분              1시간 17분                       ← 총 시간
```

**5자리 = 기둥번호 · 1~4자리 = 노선번호로 가른다.** 자료가 받쳐 준다 — 서울 표
11,239개가 전부 5자리다(실측).

### 대기는 총량만 나온다

상세 줄 합이 68분인데 머리글은 77분이었다. 9분이 어디에도 안 적혀 있다 — 서강대역
열차 대기다. `RouteSample` 의 실제 `퇴근길` 대기가 `3·4·2` 로 합 9분이고 같은 값이다.

**총량은 정확히 나오고 배분은 안 나온다.** 승차 수로 균등하게 나눈다
(9 ÷ 3 = `3·3·3`). 총합과 도착예정이 첫 번에 맞고 사람이 고칠 수 있다.
**총 시간을 모르면 대기를 아예 안 만든다** — 짐작한 값을 넣지 않는다.

### 버스 선이 자동차 경로로 그려지던 것 — 원래 있던 구멍

캡처로 첫 경로(`캡처테스트`)를 저장했더니 **999 구간이 자동차 경로로 그려졌다.**
캡처 기능의 버그가 아니었다. 로그가 이랬다.

```
GET /bus/leg?no=999&from=풍산역 정류장&to=위시티1.3단지&fromLat=…&toLat=…
  버스 999 …: 경유 정류장 0개 · 승차 후보 1개 하차 후보 1개    ← 94초 뒤에야
  버스 노선 조회 실패: TimeoutError  × 여러 번, 15초 간격
```

**163 도 0개였다.** 그래서 캡처가 아니라 그리기 자체의 문제다 — 손으로 만든
경로에도 같은 일이 벌어지고 있었을 것이다. 선은 그럴듯하게 나오니 모르고 지나간다.

**자료가 없는 게 아니라 우리가 먼저 끊고 있었다.** 실측(2026-08-28) —

```
getBusRoute  opr_ymd=20260601  ctpv_cd=41  numOfRows=1
  timeout=15  →  TimeoutError                    ← new_style_get 이 쓰던 값
  timeout=75  →  31.9초 만에 SUCCESS
  opr_ymd=20260828(자료 없는 날)  →  4.3초에 NO_DATA_FOUND
```

마지막 줄이 가른다 — **엔드포인트는 살아 있고 자료가 있는 날짜만 오래 끈다.**
키·활용신청·운영일자 문제가 아니다. 운영일자 `20260601` 은 맞는 값이다
(노선표가 매일 바뀌지 않아 고정해 둔 것이다).

같은 호스트의 다른 서비스는 빠르다 — TAGO 이름 조회 3.3초, GBIS 0.8초.

**타임아웃만 늘려서는 못 쓴다.** `bus_route_ids` 가 경기 노선표를 페이지 다섯 개로
받으니 160초가 된다. 앱이 그만큼 못 기다린다.

**이미 잘 도는 자료가 있었다.** `route_stop_lists` — 경기는 GBIS 경유정류소, 서울은
TOPIS 도착정보 — 가 정류장을 **좌표와 순번까지** 준다.

```
999번  0.8초  20753(seq 13) → 20796(seq 21)  사이 7개, 좌표 전부 있음
163번  0.4초  19132(seq 60) → 14205(seq 64)  사이 3개
```

캡처가 적어 준 `8개 정류장 이동`·`4개 정류장 이동` 과 맞는다. 그리고 사이에
**전원마을입구·동국로삼거리**가 들어 있다 — 2026-08-20 에 *"자동차 경로에는
없었다"* 고 적어 둔 그 정류장들이다.

그래서 `bus_leg_waypoints` 가 그 목록을 먼저 보고 **좌표로** 승·하차를 집는다.
이름으로는 못 가른다(`위시티1.3단지` 가 길 양쪽이고 둘 다 승차보다 뒤 순번이다).
번호가 같은 다른 지역 노선(수원 999)은 좌표가 걸러 낸다.

**옛 길은 안 지웠다.** GBIS 는 경기, TOPIS 는 서울뿐이라 다른 시도에는 그 길밖에
없다. 폴백으로 내리고 타임아웃을 `NEW_STYLE_TIMEOUT = 40` 으로 올렸다 — 15초는
자료가 와도 못 받는 값이었다.

배포 후 운영 서버에서 확인했다.

```
999  풍산역 정류장 → 위시티1.3단지   경유 정류장 7개   0.35초   (전에는 0개 · 94초)
163  국회의사당역.KB국민은행 → 신촌로터리  경유 정류장 3개   0.92초   (전에는 0개)
```

**이미 저장된 경로는 그대로다.** 좌표열은 저장할 때 박힌다 — 앱에서 같은 이름으로
다시 저장해야 새 선이 들어간다.

### `귀가` 탭을 지도와 카드로 갈랐다

설계 [`specs/2026-08-28-journey-map-cards-split-design.md`](superpowers/specs/2026-08-28-journey-map-cards-split-design.md)
· 커밋 `31826b6`

**스크롤이 불편했다.** 원인은 손짓이 다투는 것이다 — 지도가 620pt 를 차지하고
그 안의 드래그는 지도가 가져가니(`interactionModes: [.pan, .zoom]`), 페이지를
스크롤하려면 지도 밖 좁은 데를 잡아야 했다. 화면이 852pt 인데 지도가 620pt 다.

상단에 `지도 | 카드` 세그먼트를 두고 **지도 쪽은 스크롤을 없앴다.**

```
제목 + 지금 보고 있는 귀가 (아빠 · 18:04 도착 예정)
[ 지도 | 카드 ]          ← 그릴 수 있는 지도가 있을 때만
지도  남는 공간 통째로 · 여럿이면 좌우 페이지
카드  남의 카드 → "내 귀가" → 내 카드 → runStatus → plannedJourney → controls
```

지도의 `containerRelativeFrame { min(max(h*0.72, 300), 620) }` 을 없앴다. 상한 620은
*"그 이상은 어차피 한 화면에 안 들어와서"* 둔 값이라 스크롤이 사라진 지금 전제가
없다. **이 변경이 2026-08-25 사고를 구조로 없앤다** — 마커가 잘린 띠에 들어가
*"지도를 열었는데 사람이 안 보였다"* 던 것. 잘릴 띠가 없어졌다.

`watchingSection`·`travelerStripCard` 를 지우고 `otherJourneys`·`myJourney` 로
갈랐다. **귀가자 본인도 자기 지도를 본다** — 그 이유는 `HomecomingJourneySection`
주석에 있다(좌표가 틀려도 본인 화면에서 드러나야 한다).

### 지도가 사람 손을 밀어내던 것

커밋 `4c1bbaa`

확대해 둔 것이 저절로 풀렸다. 카메라를 전체 영역으로 다시 잡는 자리가 셋이다.

```

onChange(of: TravelerFrame)       좌표 갱신 — **150m 마다**   ← 실제 원인

이동 중이면 몇십 초마다 28km 전체 보기로 되돌아갔다. 정류장 하나를 자세히 보려는

버튼이 사라지고 추적이 다시 붙는다.

**확인** — 만지면 버튼이 뜨고(1), 누르면 돌아가며 사라진다(3). 위치 갱신이 와도
확대가 유지되는지(2)는 **150m 를 움직여야 재진다** — 실귀가에서 확정된다.

### 도착예정이 잠깐 튀던 것 — 서버가 답을 알면서 짐작했다

커밋 `8e0c758`

화면의 도착예정이 잠깐 크게 틀렸다가 스스로 맞아졌다. 스스로 맞아지니 원인이
안 보였다. 코드로 좁혔다.

```
세션 시작   경로가 있으면 planned_seconds 를 **안 채운다** (경로 없는 쪽만 채운다)
갱신       where_on_route 가 자리를 못 집으면 arrival 도 None

```

폴백은 `straight / speed` 라 앉아 있으면 크게 튄다. **시험으로 되재니 22분

본 증상이 정확히 그 모양이었다.

경로가 있으면 `started_at + route.total_seconds` 를 쓴다. 세션 시작에서 첫
도착예정을 만들 때와 같은 값이고 앱이 쓰는 값과도 같다.

**경로 위에서는 이 버그가 안 난다.** `remaining = total + delay − elapsed` 이고
`delay ≤ elapsed` 라 도착예정이 `now + total` 을 넘을 수 없다 — 그래서 폴백 분기가
범인이라고 좁힐 수 있었다.

자격 코드를 만지는 작업을 그 위에 얹으면 무엇이 깨졌을 때 원인을 가릴 수 없다.

### 값이 화면까지 오는 길 — 귀가자와 가족이 다르다

2026-08-31 에 재서 정리했다. 어디에도 한 장으로 안 적혀 있던 것이다.

```
귀가자 폰   ① 30초 타이머 → POST /session/{id}/bus-arrival → 응답을 받아
              앱이 activity.adopt() → activity.update()      ← 로컬. 33초
           ② 위치 보고 응답에도 상태가 실려 온다
           ③ APNs 푸시                                       ← 앱이 죽어도 온다

가족 폰     ③ APNs 푸시만. 서 있으면 heartbeat 주기라 120초
```

**`handle_bus_arrival` 은 가족에게 안 민다.** 부른 사람에게 돌려줄 뿐이다.
미는 함수(`update_activities`)를 부르는 곳은 `handle_location` 하나다.

| | 버스 도착 값이 새로 오는 주기 |
|---|---|
| 귀가자 잠금화면·아일랜드 | **33초** |
| 가족 잠금화면·아일랜드 | **120초**(서 있을 때) |

**세 길이 겹쳐 있는 것이 설계다.** 각자 못 메우는 구멍이 있다 — 30초 타이머는
승차 창 안에서만 돌고(`sawBusArrival`) `귀가` 탭이 화면에 있어야 하며, 위치 보고
응답은 보고가 나갈 때만이고, 푸시는 앱이 죽어도 온다. 그래서 **푸시를 끄면 안 된다.**

이 구조는 두 사고 뒤에 생겼다 — 화면이 27분 낡았던 것(2026-08-18, priority 5)과
한 화면 안에서 어긋났던 것(2026-08-21: 화면 3.2km, 서버 2,093m).

### 도착하면 앱 카드만 즉시 사라지던 것

커밋 `64545ca` (2026-08-31)

서버는 도착 뒤 5분을 기다렸다 `end` 를 쏜다(`ARRIVED_LINGER_SECONDS = 300`).
그래서 잠금화면과 아일랜드에는 도착 카드가 5분 남는데 **앱 카드만 0초에 사라졌다.**

원인은 `finish()` 의 `self.activity = nil` 이었다. **그건 액티비티를 끝내는 것이
아니라 앱이 참조를 놓는 것뿐이다** — 끝내는 건 `end` 다. 그런데 앱 카드가 그 참조를
보고 그린다(`isRunning`).

넷을 한 벌로 고쳤다.

```
1. finish() 가 참조를 안 놓는다                     카드가 남는다
2. activityStateUpdates 를 지켜본다                 이게 없었다
3. arrivedLingerSeconds = 300 안전망                end 가 안 와도 안 막힌다
4. reattach 의 유령 정리가 방금 도착한 것은 안 치운다   5분을 잘라 먹던 것
```

**2번이 핵심이다.** `contentUpdates` 는 **내용이 바뀔 때만** 오고 종료는 안 알려
준다. 이게 없으면 1번이 사고가 된다 — 서버가 5분 뒤 끝내도 앱은 모른 채 `귀가 시작`
을 영영 막는다. `WatchingStore`·`HomecomingPushRegistrar` 가 이미 쓰던 스트림이다.

**3번은 서버 주석이 지목한 짝을 채운 것이다.** `ARRIVED_LINGER_SECONDS` 주석이
*"앱의 `arrivedLingerSeconds` 와 같아야 한다"* 고 적어 뒀는데 **앱에 그 상수가
없었다.** 이제 양쪽 다 300이다.

`isRunning` 은 안 쪼갰다. 5분 동안 `귀가 시작` 이 막히지만, 도착하자마자 새 귀가를
시작하는 일은 없다고 사용자가 확인해 줬다.

## 오늘 새로 알게 된 함정

**`activity = nil` 은 Live Activity 를 끝내지 않는다.** 앱이 참조를 놓는 것뿐이고,
잠금화면의 알림은 `end` 푸시나 로컬 `end` 라야 끝난다. 그런데 앱 화면이 그 참조를
보고 그리므로, 놓는 순간 **앱에서만 사라진다.** 2026-08-31 에 도착 카드가 그랬다.

**`contentUpdates` 는 액티비티가 끝나는 것을 안 알려 준다.** 내용이 바뀔 때만 온다.
종료를 알려면 `activityStateUpdates` 를 따로 봐야 한다.

**화면이 실제로 갱신됐는지는 서버 로그로 알 수 없다.** 서버는 요청과 "APNs 가
접수했다" 까지만 안다 — `2/2개 화면 갱신` 은 화면이 바뀌었다는 뜻이 **아니다**
(2026-08-18 에 갱신 172건이 전부 200 을 받았는데 폰이 그린 값은 27분 낡아 있었다).
**기기 로그를 본다** — `adopt` 가 `HomecomingLog.activity` 에 찍는다.
2026-08-31 에 잠금 상태 갱신 주기를 두 번 잘못 짚은 것이 이 때문이다.

**`.task` 는 앱을 잠가도 안 멈춘다.** `UIBackgroundModes: location` 이 켜져 있어
위치 갱신이 도는 동안 앱이 잠들지 않는다 — 그래서 탭의 30초 타이머가 잠금화면에서도
계속 돈다(2026-08-31 실측, 8분간 33초 간격 무중단). **"앱을 닫았으니 안 돌 것"
이라고 짐작하면 안 된다.**

**뷰를 옮기면 거기 붙어 있던 `.task` 도 함께 사라진다.** `귀가` 탭을 가르면서 귀가자
카드를 다른 자리로 옮겼는데, 그 카드에 30초 버스 도착 갱신 타이머가 붙어 있었다 —
**앞 회차에 칩이 5분 사라진 것을 고친 바로 그 코드다.** 빌드도 시험도 다 통과했고
화면도 멀쩡해 보인다. `BusArrivalTicker` 로 떼어 **탭에** 붙였다. 목적이 *"화면이
앞에 있는 동안"* 이니 카드가 아니라 탭의 것이 맞고, 지도를 보며 버스를 기다릴 때도
돌아야 한다.

**`.animation(_:value:)` 에 `repeatForever` 를 걸면 되풀이가 안 붙는다.** 값이 바뀌는
그 한 번만 애니메이션된다. `withAnimation` 으로 시작해야 한다.

**서버가 답을 아는데도 짐작하는 분기가 있을 수 있다.** 도착예정이 그랬다 —
`planned_seconds` 가 경로 없는 세션에만 채워지는데, 폴백 조건이 그 값만 봤다.
**빈 값을 "모른다" 로 읽기 전에 다른 데 답이 있는지 본다.**

**정류장을 이름으로 찾을 때 지하철역을 먼저 보면 안 된다.** `stop_by_ars` 에서
역 표를 먼저 보게 뒀더니 **버스 기둥 `신촌로터리` 가 지하철 `신촌역` 에 걸렸다** —
570m 옆이고 시험이 잡아 줬다. `_find_station` 이 포함 관계를 헐겁게 보기 때문이다
(`서강대학교` ⊂ `서강대역` 을 맞추려고 그렇다). **번호가 있으면 그건 버스 기둥이라는
뜻**이니 정류장 표를 먼저 보고, 번호가 없을 때의 역 조회는 이름이 꼭 같아야 한다.

**기둥번호만 믿으면 안 된다.** OCR 이 한 자를 잘못 읽으면 조용히 3km 떨어진 자리가
박힌다 — `19132`(국회의사당역)를 `14205`(신촌로터리)로 읽는 식이다. **번호로 찾은
이름이 캡처의 이름과 안 맞으면 버린다.**

**화면에 다른 경로의 시간이 같이 떠 있다.**

```
고정 | 1시간 17분     ← 지금 보는 경로
최적 | 1시간 14분     ← 다른 후보. 이걸 주우면 3분이 틀린다
```

그래서 `<H>시간 <M>분` 은 **줄 전체인 것만** 받는다.

**위쪽 요약 막대는 못 쓴다.** `ㅊ 2분(표 9분 7분` 로 뭉갠다(신뢰도 0.30). 아래 상세
줄은 멀쩡하다 — 앞 회차의 *"요약 목록 화면은 못 쓴다"* 가 **한 화면 안에서도** 성립한다.

**구분자를 믿지 않는다.** 같은 자리가 장마다 `•` · `.` · `·` 로 흔들렸다
(`도보 328m • 7분` / `도보 328m. 7분`). 숫자만 잡고 사이는 느슨하게 읽는다.

**여러 장 겹침은 날 줄로 접으면 안 된다.** 같은 자리를 장1 은
`서강대역 2 번 출구까지` 한 줄로, 장2 는 `서강대역` + `번 출구까지` **두 줄로**
쪼갰다. 문법에 걸린 줄만 남긴 뒤 그걸로 접는다. **구간으로도 못 접는다** — 구간의
도착 이름이 다음 장의 승차 줄에서 오기 때문에 장1 의 마지막 도보는 이름이 비어 있다.

**타임아웃이 짧으면 자료가 와도 못 받는다. 그리고 그 실패는 조용하다.** 버스 구간이
자동차 경로로 그려지는 것으로만 드러났고, 선은 그럴듯해서 화면으로는 모른다.
**외부 API 가 느려진 것을 우리 코드가 자료 없음으로 읽었다.** 빈 결과를 받았을 때
`실패` 와 `자료 없음` 을 가르는 것이 이 저장소의 규율인데, 타임아웃은 그 사이에서
실패인데 자료 없음처럼 흘러갔다.

**공공데이터 키가 없으면 아예 부르지 않는다.** 나가 봐야 403 인데, 그 탓에 시험이
망을 타고 0.5초를 버렸다. `gbis_get` 에 확인을 넣었다. **대신 봉투 해독을 재는
시험은 키를 넣어야 한다** — `test_leg_stops.GbisGetTests` 가 그래서 깨졌고 고쳤다.

**서울은 기둥번호로 노선을 되물을 수 없다.** `stationinfo/*` 가 401 이라 서버가
`6713` 을 대신 찾아 줄 길이 없다 — `6713` 이 사는 자리가 바로 서울(`19132`)이다.
그래서 둘째 노선은 칩에 손으로 더한다.

**그게 견딜 만한지 실제로 해 보고 확인했다(2026-08-28).** 캡처로 경로를 만든 뒤
`6713` 을 칩에 쳐 넣는 것이 성가시지 않았다. 그래서 접어 뒀던 안 — `버스 도착정보
더보기` 캡처를 한 장 더 받아 서버가 후보 노선을 거르는 것 — 은 **안 만든다.**
후보당 공공데이터 호출이 한 번씩 늘고(일일 한도 1,000회) 두 번째 캡처 종류를 읽는
설계가 생기는데, 그 대가를 치를 이유가 없어졌다.

설계할 때는 *"경로당 한 번 하는 일이라 값이 안 맞는다"* 는 **내 짐작**이었다.
이제는 해 본 사람의 답이다.

## 검증

```

### 본보기를 가린 방법

`Server/fixtures/capture-{1,2,3}.txt` 는 실기기 캡처의 OCR 출력 **그대로**다.
이 저장소는 공개라 세 줄만 가렸다 — 출발지 주소, 집 아파트 이름, 집 주소.
정류장 이름과 기둥번호는 이미 인계 문서 곳곳에 적혀 있어 새로 드러나는 것이 없다
(`git grep` 으로 확인했다). `RouteSample` 이 좌표를 가려 둔 것과 같은 이유다.

## 상태

**서버** — 배포 완료. `POST /capture/parse` 살아 있음. 버스 선 고침도 배포됨. 시험 244개.

**앱** — `Woncheol's iphone` 에 오늘 것까지 설치됨(`com.kona.homecoming2`).

**경로** — 앞 회차에서 복구한 `퇴근길`(163 + 6713) 그대로. 계정 `e880109cf889`.

**실기기에서 끝까지 확인했다.** 사용자가 폰에서 캡처 세 장으로 경로를 저장했다.

```
POST /capture/parse  (e880109c)          ← 폰에서 온 것
  캡처 3장 → 구간 10개, 적어 둘 것 0개
경로 저장 91d1bf1ff0e0 — 캡처테스트 · 77분 · 구간 10개
```

`PhotosPicker(matching: .screenshots)` 로 사진이 떴고, 구간 10개·77분이 채워졌다.
버스 선을 고쳐 배포한 뒤 다시 저장하니 **999 구간이 노선을 훑는 선으로 그려졌다**
(사용자 확인). 설계할 때 의심했던 두 자리가 다 풀렸다.

**실귀가로 확인했다.** 2026-08-28 저녁(KST 18:03~18:47), 캡처로 만든 그 경로로.

```
18:03  moving  18,556m
       …       단조 감소. 되돌아간 적 없고 이탈 줄이 0이다
18:28  moving   3,184m
18:33  moving   3,132m   ← 5분에 52m. 풍산역에서 999 를 기다린 자리
18:36  moving   2,345m   ← 탔다
18:41  nearby   1,851m
18:47:33  arrived        위치 기록 20건 삭제
```

위치 보고 143회, 버스 도착 새로고침 78회, 매번 `2/2개 화면 갱신`(가족 기기까지).

| 고친 것 | 실귀가 결과 |
|---|---|
| 갱신 타이머를 카드→탭 | **확정** — 32~33초로 78회, 카드가 화면에서 빠져도 안 멈춤 |
| 값이 비어도 계속 물음 | **확정** — `없음`3회 뒤 **31초 만에 저절로 회복**, 사람이 아무것도 안 누름 |
| 지도 줌 자동 추적 끄기 | **확정** — 위치 갱신 143회 동안 확대가 유지됐다 |
| 경로 판정 | **확정** — 이탈 0, 남은거리 단조 감소 |
| 아일랜드 버스 칩 | **확정** — 31분간 떠 있었고(값 52회·없음 3회) **두 줄이어도 안 잘렸다** |
| 캡처로 만든 경로 | **확정** — 그 경로로 끝까지 갔고 도착 판정까지 |
| 도착예정 폴백 고침 | **안 걸림** — 자리를 매번 집었으니 안전망이 안 쓰였다 |

값이 빈 자리의 실측 —

```
09:17:03 없음 → 09:17:36 없음 → 09:18:09 없음 → 09:18:40 값     (UTC)
```

**아직 안 본 것** — 움직이면서 구간이 넘어갈 때. 앞 회차부터 남아 있다.

**배포 DB 의 유령 계정이 둘 늘었다.** 엔드포인트가 살았는지 재려고 `/device/register`
를 불렀다. 토큰은 셸에만 있었고 버렸다 — 앞 회차에 남은 것과 같은 종류로 해는 없다.
